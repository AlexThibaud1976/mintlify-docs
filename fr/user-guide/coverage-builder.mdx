L’onglet **Couverture** part d’**exigences** (pas d’un plan) et répond à : *de quoi ai-je besoin pour tester la non-régression de ces fonctionnalités ?* Il remonte les tests existants liés à ces exigences (`TestedBy`), signale les **trous** (exigences sans test), prévisualise un plan de non-régression et — après confirmation explicite — peut **créer** ce plan dans ADO. Read d’abord, write ensuite : vous obtenez de la valeur (analyse + spec de plan exportable) **avant** de payer le coût d’écriture. L’interrupteur **Panneau de configuration** replie la sélection d’exigences et les options pour que la matrice occupe toute la largeur ; le nombre d’exigences et les options actives restent visibles en pastilles, et **Analyser la couverture** reste dans la barre — le seul : c’est l’action principale avant l’analyse ; ensuite, la sélection se replie une fois (rouvrez-la quand vous voulez) et l’action principale devient **Créer le plan dans ADO** (nom du plan, exports et cible sous *Options de création*). Le tableau se lit Exigence · État · Tests (· Plans) ; l’évaluation et le code lié tiennent en une pastille d’une ligne, le détail par ligne.

## Sélectionner des exigences & lire la couverture {#coverage-select}

Sélectionnez des exigences par **area path**, **itération**, **requête WIQL** ou liste d’**IDs** — vous partez des fonctionnalités à couvrir, pas d’un plan existant. TestPulse Studio résout alors, pour chaque exigence, les cas de test liés via `TestedBy` (la même primitive de lien qu’ailleurs, juste dans le sens exigence→test) et classe chacune en **couverte** (≥1 test lié) ou **trou** (aucun test lié). La composition n’utilise **que le graphe de liens** — aucun outcome/point/run n’est lu, et aucune nouvelle permission n’est requise. Des cartes de synthèse résument total / couvertes / trous / tests liés. **100 % de trous est un résultat valable** (un plan fait de suites vides, prêtes à remplir), jamais une erreur.

## L’état optionnel « couverte non planifiée » {#coverage-unplanned}

Un troisième état — *couverte non planifiée* (un test existe pour l’exigence mais n’est dans aucun plan, on veut donc le réutiliser plutôt que le réécrire) — est disponible derrière un **toggle « Scan planification » opt-in, OFF par défaut**. Il est plus coûteux : il doit énumérer plans → suites → cas de test pour savoir si chaque test est déjà planifié. Ce coût est signalé, et l’état n’est **jamais affiché sans scan réel**. Sans le toggle, le cœur reste à deux états nets (couverte / trou).

## Preview du plan & export read-only {#coverage-export}

À partir du résultat de couverture, TestPulse Studio construit une **spec de plan** : une suite requirement-based par exigence sélectionnée, chacune avec ses cas de test prévus (auto-peuplés) et un indicateur de trou. Une **preview** montre ce qui serait créé (ex. « 9 suites requirement-based, 34 cas de test »). Le bouton **« Exporter la spec »** est **toujours disponible et ne requiert aucune permission** — il sérialise la spec en **JSON, Markdown ou CSV**, de sorte qu’un responsable qualité sans droit d’écriture garde toute la valeur read (monter le plan à la main, ou le transmettre). L’export reflète exactement la preview.

## Créer le plan dans ADO (écriture — permission + confirmation) {#coverage-create}

**La création de plan est la première fonctionnalité de TestPulse Studio qui écrit dans Azure DevOps.** Depuis la preview, **« Créer le plan dans ADO »** ouvre un **dialog de confirmation** récapitulant exactement ce qui sera écrit (N suites requirement-based, M tests auto-peuplés, K suites-trous vides). **Rien n’est écrit avant votre confirmation.** À la confirmation, TestPulse Studio crée le plan et une suite requirement-based par exigence — ADO **auto-peuple** les couvertes depuis `TestedBy` et laisse les trous **vides** (échafaudage vivant : le jour où un test est écrit et lié, il apparaît tout seul). C’est de la **création seule** — jamais de modification/suppression d’un plan/suite/test existant ; une **collision de nom avertit** au lieu d’écraser ; un **échec partiel rapporte** exactement ce qui a été créé. La création du plan utilise le scope **`vso.test_write`**, déjà déclaré par TestPulse Studio et accordé à l’installation de l’extension ; elle n’écrit qu’après votre clic, avec vos droits.

## Choisir l’area path & l’itération — et le 403 « permission ≠ scope » {#coverage-target}

Avant de créer, la preview vous laisse **choisir l’area path** (et, en option, l’**itération**) sous lequel le nouveau plan sera créé. C’est le champ qui corrige l’échec de création le plus courant : un **403 — *vous n’avez pas les permissions appropriées pour gérer les plans de test sous cet area path***. Azure DevOps accorde la permission *Manage test plans* **par area path** ; si vous n’en choisissez pas, le plan est créé sous la **racine du projet**, où vous n’avez peut-être pas ce droit. Choisissez une area où vous l’avez, et la création réussit. Laissez les deux vides et le comportement est inchangé (racine projet, comme avant) ; les listes sont lues depuis les classification nodes du projet via le **scope `vso.work` existant** — aucune nouvelle permission — et si elles sont illisibles vous pouvez toujours saisir un chemin à la main. **Ce 403 n’est pas un problème de scope.** `vso.test_write` est déjà accordé ; l’erreur est une **ACL d’area path**. TestPulse Studio le dit maintenant honnêtement : un 403 de permission vous oriente vers *Manage test plans sur l’area path choisi* (à demander à votre administrateur), et le message « ajoutez le scope » n’apparaît **que** lorsque le scope est réellement en cause (ex. un 401).

## Évaluer la *profondeur* de couverture — « est-ce bien couvert ? » {#coverage-depth}

La couverture simple est **structurelle** : une exigence avec ≥1 test lié est « couverte », même si un unique smoke test trivial tient lieu de cinq critères d’acceptation — fausse confiance. Activez le toggle opt-in **« Évaluer la profondeur de couverture »** (OFF par défaut ; off ⇒ l’onglet Coverage est strictement inchangé) et, après *Analyze coverage*, TestPulse Studio ajoute une colonne **Profondeur** avec une bande par exigence :
- **Bien couverte** — les tests semblent couvrir les critères d’acceptation.
- **Partielle** — des critères ou chemins sont probablement manquants.
- **Superficielle** — trop peu de tests, ou des tests sans étapes.
- **Trou** — aucun test lié.
- **Sous-spécifiée** — pas (ou peu) de critères d’acceptation pour évaluer.

Dépliez une ligne pour voir les **constats** (les raisons, avec liens ADO) et des **axes d’amélioration** concrets (« ajoutez un test négatif pour… », « étoffez les N tests sans étapes », « confirmez qu’un test couvre *X* »). L’analyse est **100 % déterministe et sans IA** — elle compte les critères d’acceptation, mesure la profondeur des étapes, repère les mots-clés négatif/limite (**FR + EN**), vérifie le recouvrement de termes et l’exécution. Elle est **purement advisory** : elle ne bloque rien, n’alimente pas le score qualité / GO-NO-GO, ne change aucun résultat. Le wording est volontairement prudent (« possible », « apparent ») — c’est un signal « à revoir » ; **vous** décidez. Elle est **en lecture seule** (le contenu des tests est lu via la primitive batch existante — aucun nouvel appel ni scope ADO) et se dégrade gracieusement par exigence (un test sans étapes compte quand même ; aucun critère d’acceptation ⇒ *Sous-spécifiée*, jamais un verdict inventé).

## Axes d’amélioration proposés par l’IA {#coverage-axes}

Après **Analyser la couverture**, le panneau **Axes d’amélioration** sous le tableau peut **proposer des axes** avec l’assistant IA. L’IA ne fait que commenter l’analyse déjà calculée : elle ne recalcule rien et n’écrit rien. Chaque axe a une priorité (1 à 3), une courte justification, les exigences concernées (un clic mène à leur ligne) et **une** action : **Concevoir les tests** (ouvre Conception sur cette exigence, les techniques manquantes pré-cochées), **Voir les tests non planifiés** (filtre le tableau ; « Lancer le scan de planification » si le scan n’a pas été fait) ou **Comparer des doublons** (ouvre les tests cités dans Azure DevOps). L’en-tête indique quel modèle a proposé les axes et quand, avec une étiquette IA.

**Garde-fous.** Un axe qui cite une exigence hors de la sélection est écarté et compté ; un axe de doublons doit citer au moins deux tests présents dans l’analyse. Au plus **40 exigences** partent, les premières par priorité — le panneau le dit. Descriptions et critères d’acceptation ne partent que si la catégorie « texte des exigences » est cochée dans l’administration du projet, *Assistant IA › Fonctions et données*. Si l’analyse ou la sélection change, les axes sont grisés (« analyse modifiée ») jusqu’à une nouvelle proposition. Rien n’est conservé.

**Boucher un trou.** Depuis Conception, une fois les cas écrits, **Revenir à la couverture et réanalyser** ramène sur cet onglet avec la même sélection et relance l’analyse une fois.

## Signal de couverture de test sur la fiche {#wit-coverage-signal}

TestPulse Studio fait aussi remonter la couverture **là où PO et devs travaillent déjà — sur la fiche elle-même**. Ouvrez une User Story / PBI : un **onglet « Couverture »** dédié apparaît sur le formulaire (une contribution en lecture seule, isolée du hub — le reste de TestPulse Studio est inchangé). L’onglet est **auto-placé** et **monté au clic**, donc **aucune lecture** tant que vous ne l’ouvrez pas — la fiche reste rapide. À l’ouverture, il rend un **headline instantané** : deux pastilles bon marché — **Couverture** (`Couvert (N)` / `Non couvert`, depuis les liens `TestedBy`) et **Profondeur** (`Bien couverte / Partielle / Superficielle / Trou / Sous-spécifiée`, depuis le **même analyseur** sur critères d’acceptation + description + contenu des tests liés) — **sans aucune lecture de résultats**. Puis le détail **se charge automatiquement** (plus de dépliage manuel) : un bloc **analyse de profondeur** (les constats, ex. *« aucun critère testable détecté »* pour Sous-spécifiée), une **synthèse chiffrée** (compteurs `en échec` / `bugs` / `échec-sans-défaut` + dernière exécution), et un **tableau des tests** avec le **pass/fail « Dernière »** (outcome le plus récent agrégé par cas de test, échecs en tête), le **bug derrière chaque test en échec** (#id, sévérité, état, assigné), et les **tests en échec sans défaut tracé** (réutilise la logique). Tout est **en lecture seule et live (Modèle A)** — calculé directement depuis l’US, **indépendant de tout rapport TestPulse Studio publié**. Il **réutilise** les moteurs existants (profondeur, statut de traçabilité, échec-sans-défaut) au lieu de les réimplémenter, n’utilise que les scopes **déjà accordés** `vso.work` + `vso.test` (**aucun nouveau scope, aucune nouvelle dépendance, jamais d’écriture**), et **ne lit jamais les commentaires**. Le pass/fail vient de la résolution de chaque cas de test vers son plan/suite (`testplan/suites?testCaseId`, api-version 7.1, confirmée sur Server 2022.1) → l’endpoint de points existant → une agrégation « Dernière » ; les bugs, de la requête WIQL cas-de-test→bug existante. Il y a un **cache par fiche** (revenir sur une fiche ne re-fetch pas), et un timeout court dégrade en un discret *« couverture indisponible »* — jamais une erreur sur la fiche. Une US **sans test lié** affiche un état neutre *Aucun cas de test lié* (et saute complètement le fetch) ; des critères d’acceptation vagues/vides affichent *Sous-spécifiée* honnêtement plutôt qu’un score inventé. *(L’onglet apparaît sur tous les types de work item ; là où la couverture n’a pas de sens — un Bug, une Task ou un Test Case — l’état neutre le couvre proprement.)*

L’onglet respecte **les deux langues** : il s’ouvre dans la locale **auto-détectée** et porte son **propre sélecteur FR/EN** (en haut à droite), mémorisé **localement dans le navigateur**, **sans appel ADO**. Sa présentation a été **rafraîchie** — **deux cartes verdict colorées encadrées** (couverture, profondeur), chaque section dans une **carte nettement encadrée** à en-tête coloré, une synthèse en **tuiles** et un tableau à **pastilles d’outcome** et tags de type de test (mêmes données, lecture plus claire ; la profondeur reste honnête, jamais un score inventé).

**Sélecteur de portée.** Quand une US couvre **plus d’un plan de test**, un **sélecteur de portée** apparaît au-dessus du détail : **« Dernière (tous plans) »** (le défaut — l’outcome le plus récent tous plans confondus, exactement comme avant) ou **un plan de test précis** (façon Xray). Choisissez un plan : l’onglet **masque les tests qui n’y sont pas** (une ligne *« X test(s) dans ce plan sur N liés »* rend le masquage explicite) et **recadre** le statut testé, les échecs, le drapeau échec-sans-défaut et la fraîcheur **sur ce plan** — tandis que **Couverture, Profondeur et la liste des bugs restent plan-indépendantes** (un bug est lié à un cas de test, pas à un plan). Le changement de portée est **instantané et en mémoire** — **aucun nouvel appel ADO** (les résultats par plan ont déjà été récupérés à l’ouverture de l’onglet) — et votre choix est **mémorisé par fiche** (localement, sans écriture ADO), avec repli gracieux sur *Dernière* si le plan mémorisé ne s’applique plus.

**Bandeau verdict d’exécution.** Le détail s’ouvre désormais sur un **verdict d’exécution** coloré — **Réussi** (vert), **Non OK** (rouge), **Non exécuté** (gris) ou **Non couvert** (neutre) — pour lire *est-ce que ça passe ?* d’un coup d’œil, pas seulement *est-ce couvert ?*. C’est une **réduction pure** des tests déjà affichés, à **précédence stricte** (pas de « partiel ») : **au moins un Failed ⇒ Non OK** ; sinon **au moins un non-passé** (`Blocked`, `NotApplicable`, `NotExecuted`, `Inconclusive`, `None`) **⇒ Non exécuté** ; **seulement 100 % Passed ⇒ Réussi** ; **0 test lié / non couvert ⇒ Non couvert**. Il respecte le **sélecteur de portée** (il donne le verdict du *plan sélectionné*) et **se recalcule en mémoire** au changement de portée — **aucune lecture nouvelle**. Affiché avec **icône + libellé** (jamais la couleur seule ; couleurs explicites robustes en thème clair et sombre), c’est un **axe distinct** de la couverture et il **ne recolore jamais la carte Couverture** (« est-ce testé ? » vs « est-ce que ça passe ? »).

**Navigabilité.** Le tableau des tests est désormais **triable et rebondissable**. **Cliquez n’importe quel en-tête** — **#, Test, Outcome, Last run, Bug** — pour trier, et re-cliquez le même en-tête pour **inverser** le sens (`aria-sort` reflète la colonne active). Outcome trie via le **même rang** que la vue par défaut (échecs d’abord, Passed en dernier), Test par **nom** (le préfixe `[tag]` est ignoré), Last run chronologiquement (les tests jamais exécutés en fin). Votre **tri est mémorisé par fiche** (localement, sans écriture ADO) et l’**ordre par défaut est inchangé**. Deux **sauts en un clic** sont ajoutés : une ligne **exécutée** (un vrai run derrière elle) lie depuis sa cellule **Last run** vers le **run de test** (`_testManagement/runs`), et quand un **plan précis** est cadré, un lien **« Exécuter dans Azure DevOps »** s’affiche près du sélecteur de portée, ouvrant la vue **execute** du plan (`_testPlans/execute`). Les deux s’ouvrent dans un **nouvel onglet** (`rel="noopener noreferrer"`) et sont des **navigations portail, pas des appels API** — le run id était **déjà lu**, donc **aucun nouvel appel, scope ni dépendance** ; les liens **dégradent gracieusement** quand l’URL hôte est indisponible.

**Aperçu des plans dans la couverture.** Dans le **Coverage builder**, avec le **Planning scan** activé, une colonne **Plans** montre, par exigence, où ses tests liés sont planifiés — le nom du plan si unique, **« N plans »** si plusieurs, **« — »** pour un trou (ou quand le scan est off). **Dépliez une ligne** pour lister chaque couple (plan, suite) avec un lien **« Exécuter dans Azure DevOps »** vers la vue **execute** du plan ; une lecture **lazy** (au dépliage seulement, une fois par suite, dégradation silencieuse) remplit une progression **n/m run**. Le détail des plans est extrait des **mêmes** réponses `suites?testCaseId` que le scan reçoit déjà — **aucun appel supplémentaire au chargement de la table**. Tous les liens plan applicatifs ciblent désormais **execute** (et non la vue de composition) via un unique builder d’URL partagé.

**Résolution config-correcte.** Quand **un même cas de test** couvre **plusieurs US sœurs qui ne diffèrent que par la configuration de test** (un motif récurrent sur le terrain : un cas de test partagé, une requirement-based suite par pays/config — ex. QUAL_IT / QUAL_SG / QUAL_KR), l’onglet affichait jusqu’ici l’**outcome le plus récent tous configs confondus**, si bien qu’une US Italie pouvait afficher par erreur un run Singapour. Il **résout désormais au niveau du test-point** : une US ayant une **requirement-based suite** (`suiteType="RequirementTestSuite"`, correspondant à cette US) restreint la « Dernière » à **ses propres résultats de configuration** avant de prendre le plus récent — une US sans requirement-based suite garde le comportement précédent (« dernière globale »), inchangé. Cela réutilise des données **déjà lues** par l’onglet (le lecteur de points et les réponses `testplan/suites` exposent `suiteId`, `resultId`, `configurationId/Name` — ils étaient simplement jetés avant) ; **aucun appel API nouveau**. Deux liens gagnent en précision : le **lien run** pointe désormais vers le **résultat exact** (`&resultId=`) quand la sonde confirme qu’il est peuplé (sinon le lien se rabat sur le run sans id de résultat inventé — jamais une valeur codée en dur), et chaque ligne peut ouvrir la **suite exactement exécutée** (`_testPlans/execute` avec son `suiteId`) plutôt qu’une **page de plan vide**. Les libellés de plan du sélecteur de portée s’affichent en **« &#123;plan&#125; · &#123;config&#125; »** quand une configuration est connue, inchangés sinon.

**Ce qui a changé depuis le dernier run.** Le badge « Modifiée après le dernier run » signalait qu’une US avait changé mais pas **quoi**. Il porte désormais un bouton **« Afficher le détail »** : le déplier déclenche **une seule lecture lazy** (jamais au chargement de la fiche, seulement au premier dépliage, puis mise en cache — replier puis redéplier ne relance jamais l’appel) de l’historique des révisions de l’US, collapsé **cumulativement** depuis la date du run (plusieurs modifications depuis le run sont fusionnées en un seul avant/après, pas seulement la dernière édition). Seuls les **champs métier** sont listés — Titre, Critères d’acceptation, Description, État, Priorité, Itération, Tags — les champs de gestion système (Rev, Watermark, ChangedDate…) sont filtrés. Les champs scalaires (État, Priorité…) affichent un simple **avant → après** ; les champs riches (Critères d’acceptation, Description) reçoivent un petit **word-diff maison** (sans dépendance) qui **surligne le texte ajouté**, avec un repli côte-à-côte si le HTML est trop irrégulier pour un diff exploitable. Un changement de Critères d’acceptation ou Description porte un badge **« Alimente la profondeur »**, puisque ce sont exactement les champs lus par l’analyseur de profondeur. Un bloc distinct liste les **pièces jointes ajoutées ou retirées** depuis le run (totalement absent s’il n’y en a aucune — jamais un espace réservé vide). Lecture seule, un nouvel endpoint (`workItems/{id}/updates`, déjà couvert par le scope `vso.work` existant), strictement opt-in.
