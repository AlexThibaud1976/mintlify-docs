**Où.** Étape 5 **Automatiser** de **Design**, et la section **Tests automatisés** de l’onglet **Exigence**. La fonction **Tests automatisés** doit être active (**Assistant IA › Fonctions et données**).

**Ce que vous choisissez.** Des cas manuels de l’exigence — liés dans Azure DevOps (Tested By), ou conçus dans la session et écrits (étape 4) —, l’une des 8 combinaisons framework · langage (Playwright · TypeScript par défaut, Selenium v4 · Java (JUnit 5), Cypress · JavaScript, Playwright · Python, Playwright · C# (.NET, NUnit), Cucumber · JavaScript, Cucumber · Java, Cucumber (pytest-bdd) · Python), et le code lu à l’étape 0 (**Lire le code**). La dernière combinaison est mémorisée par projet, pour vous. Ce qui part : les étapes, attendus et données des cas, le titre de l’US, et le code lu si vous le joignez.

**Ce que fait Studio.** Un test automatisé par cas manuel, rien de plus. L’assistant IA écrit le code de chaque étape manuelle ; Studio écrit les fichiers : arborescence et noms, Page Object (ou, pour Cucumber, le `.feature` repris du cas Gherkin **sans IA** et les définitions d’étapes), la table de données tirée des itérations du cas, le titre `[TC <id>]` et le tag `@tc:<id>` (`tc_<id>` là où le framework refuse « : », comme pytest).

**Statut honnête.** Chaque sélecteur, route ou message doit être cité dans le code lu (fichier, ligne ± 3). Ce que le code lu n’établit pas devient un marqueur `À COMPLÉTER (TestPulse Studio) : <raison>` dans le fichier, et le test est un **squelette** (`test.fixme`, `@Disabled`, `it.skip`, `[Ignore]`, `pytest.mark.skip`, étape en attente) ; sans marqueur, il est **prêt à relire** — jamais « prêt à exécuter » : Studio n’exécute rien et ne donne aucune note. Une vérification de syntaxe légère par langage signale un fichier cassé, qui reste visible — et un test dont un fichier (le sien, le Page Object qu’il appelle, les définitions d’étapes) a une erreur de syntaxe n’est jamais prêt à relire (marqueur « erreur de syntaxe »). Une étape dont le corps n’a aucune instruction (commentaires seuls, `pass`, `return` seul) n’est pas reliée. Les marqueurs de l’assistant (`# todo`, `// TODO`, `# FIXME`, « à compléter ») deviennent des marqueurs Studio ; sur une étape **complète** — au moins une citation, toutes retrouvées, aucune valeur construite, aucun marqueur de Studio —, la remarque de l’assistant devient une **note de relecture** (`Note de relecture (TestPulse Studio) : …`), affichée sans bloquer et comptée à part dans les contrôles. En **Selenium**, les actions s’écrivent en ligne (`driver.findElement(By…)`, `wait.until(…)`) : aucun Page Object n’est proposé.

**Citations retrouvées dans tout le code lu.** Une citation absente de la ligne dite ± 3 est cherchée dans tout le fichier cité, puis dans les autres fichiers lus si elle n’y figure qu’une fois : elle est **recalée** (`source : fichier:ligne (recalée)`). Les formes d’un identifiant de test sont équivalentes (`getByTestId("x")`, `[data-testid="x"]` et `data-testid="x"` dans le code lu), et une valeur construite par un gabarit du code lu (`error-<champ>`) est retrouvée comme **valeur construite**. Une chaîne écrite par l’IA et coupée par une apostrophe (« n’est » entre apostrophes droites) est réparée par Studio avant la vérification de syntaxe. Avec Cucumber, un cas en étapes + données n’est **pas proposé** (Gherkin requis) — dit en gris, jamais comme un échec. Un `.feature` n’emploie qu’une langue de mots-clés, celle de la majorité des mots-clés du scénario (les mots-clés Gherkin écrits par Design restent en anglais), et la précondition du cas devient son `Background`.

**Page d’accueil, URL de base, messages composés, identifiants.** Ouvrir la page d’accueil (`/`, ou l’URL de base de chemin `/` — `page.goto("/")`, `cy.visit("/")`, `driver.get(baseUrl)`, `browser.url("/")`) n’exige pas de citation : le test dit **racine de l’application**, une source comme une citation retrouvée ; une citation de l’IA qui désigne la racine (« / », `baseUrl`, `baseUrl + "/"`) n’est jamais convertie en marqueur. Une URL absolue est acceptée quand son origine (hôte et port) figure dans un fichier lu — `playwright.config.ts`, `vite.config.ts`, le serveur, le README —, sinon elle reçoit le marqueur « URL de base à confirmer ». Un message construit par le code à partir de deux valeurs (`MSG-08 — <libellé>`, depuis une table de messages) est retrouvé quand ses morceaux sont sur une même ligne d’un fichier lu et qu’un gabarit de ce fichier les assemble : **message composé**. Un identifiant de test cité dans le mauvais fichier est retrouvé par sa **déclaration** (`data-testid=`, `id=`, `name=`) dans un écran lu ; les tests existants et la documentation ne rendent plus une valeur ambiguë. Une précondition qui utilise des paramètres du plan devient la première étape du `Scenario Outline` au lieu d’un `Background`.

**Un sélecteur vaut par sa déclaration dans l’écran.** Un identifiant de test n’est accepté que par sa déclaration dans un écran lu (`data-testid=`, `id=`, `name=`) ou un gabarit d’un écran ; une mention dans le README ou dans un test existant n’est jamais une source — elle est montrée en indice à côté du marqueur « déclaration non trouvée dans les écrans lus ». Un texte ou un message vu seulement dans la documentation ou un test est marqué aussi. **Bornes de l’écran vérifiées** : quand un test saisit dans un champ une valeur que l’écran ne prendrait pas telle quelle — valeur d’itération ou valeur écrite en littéral, quel que soit le framework (`fill`, `type`, `pressSequentially`, `sendKeys` en ligne ou via le Page Object, `setValue`, et les définitions d’étapes BDD, où la valeur est celle que l’expression de l’étape lie à chaque itération) ; plus longue que son `maxLength` (le navigateur la tronque), plus courte que son `minLength`, hors de ses `min` / `max` ou de son `pattern`, absente des options d’une liste, ou non numérique pour un champ numérique —, Studio pose au-dessus de la ligne le marqueur « valeur non saisissable telle quelle (maxLength 20) — itération 2 », avec deux issues : tester la règle par l’API, ou corriger la donnée du cas ; le test n’est jamais prêt à relire, et les contrôles comptent ces valeurs. **Données du cas jamais ignorées** : dans un test itéré (boucle sur les données, `@ParameterizedTest`, `[TestCaseSource]`, `pytest.mark.parametrize`, `Examples`), une saisie écrite en littéral égale à la valeur d’une seule itération, ou une colonne qui change d’une itération à l’autre et que le test ne lit nulle part, reçoit le marqueur « valeur fixée par le test au lieu de la donnée « telephone » — les itérations ne varient pas » : le test rejouerait la même itération ; il reste squelette. La valeur saisie est retrouvée aussi par ses accesseurs (`data.telephone()`, `getTelephone()`, `row["telephone"]`, `row.get("telephone")`, `row.Telephone`, déstructuration) pour le contrôle des bornes. **Un marqueur, jamais « prêt »** : tout marqueur Studio dans un fichier du test le laisse squelette, y compris dans une définition qu’aucune étape ne lie ou une méthode du Page Object qu’aucun test n’appelle ; une citation de l’IA non retrouvée est marquée sur la ligne qui écrit sa valeur (`getByRole(…, { name: … })` compris), et l’alerte « convertis en marqueurs » ne cite que des valeurs effectivement marquées. Quand une configuration de tests est lue (`testDir` de `playwright.config.ts`…), les fichiers Playwright · TypeScript générés vont sous cette racine ; **Prochaines étapes** dit la racine lue.

**Une liste déroulante se sélectionne, elle ne se tape pas.** Quand un test saisit une valeur dans un `<select>` de l’écran lu (`fill`, `type`, `sendKeys`…), Studio pose au-dessus de la ligne le marqueur « liste déroulante remplie comme un champ de saisie » : la sélection d’option du framework est attendue (`selectOption`, `select`, `SelectOptionAsync`, `Select`). Un sélecteur à clé (`select[name="country"]`, `[data-testid="x"]`, `#id`, `By.id`, `By.name`) désigne un élément déclaré dans l’écran : la citation de cet identifiant seul, dans le README par exemple, est rapportée à sa déclaration.

**Une seule façon de retrouver, quelle que soit la combinaison.** Un sélecteur, un texte ou une route que le test utilise est cherché par Studio lui-même dans le code lu, de la même façon que les citations de l’IA : un identifiant de test par sa déclaration dans un écran (`By.id` cherche un `id`, `By.name` un `name`), un sélecteur de balise (`h1`) par la balise de l’écran, un texte ou une route par sa seule occurrence hors tests et documentation — un texte attendu présent dans l’écran et dans un validateur est pris dans l’écran. Le résultat ne dépend plus de ce que l’IA a cité, ni de la combinaison. Avec Selenium, les bornes de l’écran sont vérifiées aussi quand l’élément est rangé dans une variable avant `sendKeys`, et `assertEquals` / `getText().contains` sont des textes attendus. Avec pytest-bdd, une définition d’étape ne relie que les étapes de son mot-clé (`@when` ne relie pas une étape `Given`), comme pytest-bdd ; Cucumber ignore le mot-clé. Une valeur saisie par le test qui n’est pas une donnée du cas (`fill("Bureau")`) est signalée par un commentaire au-dessus de la ligne et comptée, sans marqueur. Sur un fichier de définitions partagé par plusieurs tests, le compteur de l’aperçu dit aussi combien comptent pour le test montré.

**Page Object seulement s’il a un contenu.** Le fichier Page Object n’est produit que s’il a au moins une méthode ; sinon, pas de Page Object, et les tests ne l’importent pas et ne déclarent pas `po`. Un appel `po.<méthode>(…)` d’une méthode que l’assistant IA n’a pas écrite est marqué « méthode du Page Object absente » et son étape n’est pas reliée. Générer dans le Page Object les localisateurs cités par les tests est prévu, pas fait.

**Forme du code contrôlée.** Une ligne écrite dans un autre langage que celui de la combinaison (`await page.…` dans un fichier Java ou Python, l’API Playwright de JavaScript — `getByTestId`, `toHaveText` — dans un fichier Python et celle de Python — `get_by_test_id` — dans un fichier Java, C# ou JavaScript, `public void` dans un fichier JavaScript…) et un test déclaré dans un test (`it(…)` dans le corps d’un `it`, `@Test` dans une étape) sont marqués, et leur étape n’est pas reliée ; l’autre langage figure aussi parmi les erreurs de syntaxe. En JavaScript et TypeScript, quand l’assistant IA enveloppe tout le code d’un test dans son propre bloc de test (`it(…)`, `test(…)`, `describe(…)`, ouvert à la première étape et fermé à la dernière), Studio n’en garde que le corps avant tout contrôle, et note la correction dans **Journal et échecs** (« Gardée, écarts marqués ») ; un bloc jamais fermé, ou suivi d’autre code, reste marqué. Un résultat attendu positif (accepté, enregistré, créé) est demandé vérifié par le témoin de succès que montre le code lu (`save-success`), avec une attente explicite — l’absence d’erreur seulement en complément. Pour un refus, le témoin est le message d’erreur lu (`error-street`, son texte MSG-xx) : une étape de refus n’est jamais marquée faute de témoin positif. Une sous-règle sans témoin dédié (« le code postal respecte la règle de longueur ») se vérifie par ce que le code expose — témoin global, valeur conservée, absence de son erreur — avec une note de relecture, jamais un élément à compléter ; un élément à compléter écrit par l’assistant IA le reste. L’assistant IA reçoit aussi la table des éléments déclarés dans les écrans lus (sélecteur, élément, name, libellé, texte affiché, fichier, ligne). En Cucumber, une expression d’étape qui ne diffère de la liaison attendue que par sa forme (`{string}` pour `{}`, apostrophe, ponctuation finale) est reliée à la liaison attendue et comptée dans les contrôles ; des mots différents ne le sont jamais. Un cas absent de la réponse de l’assistant IA est redemandé seul, une fois, avec les méthodes et définitions déjà écrites (compté dans les contrôles, et noté dans **Journal et échecs**) ; il reste « sans résultat exploitable » seulement si la seconde réponse l’omet aussi. Dans un fichier Python, l’API Playwright de JavaScript est **traduite par Studio** avant tout contrôle (`getByTestId` → `get_by_test_id`, `{ name: x }` → `name=x`, `toBeVisible()` → `expect(…).to_be_visible()`, `await` et `;` retirés), la ligne précédée de `# TestPulse Studio : API JS traduite en Python` et comptée dans les contrôles ; ce qui ne se traduit pas reste marqué. Une citation nue (`country`) introuvable comme texte est cherchée comme `data-testid`, `id` ou `name` déclaré dans un écran, et le texte d’options collées (`SuisseFranceBelgique`) comme suite d’options d’un même `<select>`. En Cucumber, l’assistant IA reçoit l’expression de liaison attendue de chaque étape (un `<x>` sans guillemets est un paramètre anonyme `{}`), et Studio contrôle la liaison comme le framework la fait. Les bornes de l’écran sont aussi contrôlées sur les valeurs passées à une méthode du Page Object : l’argument de rang *n* (ou nommé) de l’appel est la valeur du paramètre de rang *n* (ou de ce nom) de la méthode, quel que soit le langage, même quand le paramètre porte le nom du champ (`fill(phone)` dans `getByTestId("phone")`) ; une donnée passée à une méthode qui ne la lit pas, ou que la méthode remplace par une valeur fixée, est marquée « valeur fixée par le test au lieu de la donnée ». En BDD, un cas que l’assistant IA omet dans sa liste de tests, alors que ses définitions d’étapes relient le scénario, n’est pas « sans résultat exploitable » : il est lu par ses définitions (noté dans **Journal et échecs**).

**Aperçu.** Fichier par fichier, l’étape manuelle en regard de ses lignes, les marqueurs surlignés ; le compteur au-dessus du code est celui du fichier montré (« aucun élément à compléter dans ce fichier » sur un Page Object sans marqueur, même si le test est squelette). **Modifier en place** recalcule le statut ; **Régénérer ce test** redemande à l’IA ce seul cas. **Citations rendues par le modèle** (bloc replié, sans IA, rien d’envoyé) : chaque valeur citée par l’IA, le fichier et la ligne donnés, et ce que le contrôle en a fait — retrouvée, recalée, valeur construite, message composé, retrouvée pour un texte attendu seulement, racine de l’application, ou non retrouvée, avec la raison (absente du code lu, vue seulement dans la documentation ou un test, déclaration non trouvée dans les écrans lus).

**Ce que veut dire « prêt à relire ».** Il établit que chaque sélecteur, route et message du test est retrouvé dans le code que vous avez lu, à l’endroit indiqué, que les valeurs des itérations tiennent dans les bornes de l’écran lu, et que la vérification de syntaxe est passée. Il n’établit pas que le test passe : Studio n’exécute rien — ni navigateur, ni build, ni test —, ne voit ni l’application en marche ni le code que vous n’avez pas lu, et ne donne aucune note. Relisez-le, exécutez-le dans votre pipeline, puis reliez-le.

**Livraison.** **Télécharger l’archive .zip** (produite dans le navigateur), ou **créer une pull request sur une branche neuve** `testpulse-studio/tests-auto/us-<id>` (suffixée -2, -3… si elle existe) depuis la branche par défaut du dépôt choisi, après une confirmation qui énonce dépôt, branche, fichiers et message de commit. Un fichier déjà présent sur la branche par défaut est modifié. C’est un écart de parité assumé avec l’outil dont viennent ces combinaisons : **ni commit direct, ni push sur une branche existante**.

**Relier les tests aux cas manuels.** Facultatif, après une livraison, décoché par défaut : AutomatedTestName, AutomatedTestStorage et AutomatedTestType sont écrits avec vos droits, après un contrôle de révision. **AutomationStatus n’est jamais forcé à « Automated » pour un squelette** ; AutomatedTestId n’est jamais écrit — l’association native d’Azure Test Plans vise les tests publiés par un pipeline.
