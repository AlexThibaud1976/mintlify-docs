**Où.** Sous la liste des fichiers de **Lire le code** (étape 0 **Exigence** de **Conception**, et l’onglet **Exigence**). **Confronter au code** est actif quand du code a été lu et coché, que la catégorie **Code source** est active et que la fonction **Confrontation au code** l’est (**Assistant IA › Fonctions et données**) ; sinon le bouton dit pourquoi.

**Les écarts.** L’assistant IA compare l’exigence, le modèle de test et les cas existants aux fichiers lus. Chaque écart a son type — règle absente du code lu, contrôle absent de l’exigence, valeur différente, non concluable depuis le code —, la règle concernée, les lignes de code citées (surlignées, avec un lien vers le fichier à la version lue) et une confiance. Une règle sans trace est dite absente **des fichiers lus** : le code lu est partiel.

**Vérifié par Studio.** Un écart qui cite un fichier non envoyé, des lignes hors de l’extrait envoyé, une règle inconnue ou une valeur absente des lignes citées est écarté et compté en bas, jamais montré comme un résultat.

**Citations exactes.** Chaque fichier lu part avec ses numéros de ligne : l’assistant cite les numéros qu’il voit. Un écart dont les lignes citées sont toutes vides, ou dont le code cité (entre backticks) n’est pas dans le fichier lu, est écarté aussi. Quand le code cité est à quelques lignes (10 au plus) dans le même fichier, Studio y déplace la citation et l’indique (**citation recalée**). Une valeur proposée doit figurer dans les lignes citées — ou être acceptée par une expression régulière qui s’y trouve —, et une règle issue du code doit en reprendre les nombres et les textes entre guillemets. Un écart « règle absente du code lu » dont au moins deux éléments de la règle (nombres, textes entre guillemets, codes de message, mots en capitales) figurent dans un même fichier lu devient **non concluable depuis le code**, et Studio dit où ces éléments apparaissent.

**Dépendances non lues.** Sous la liste des fichiers, Studio liste, sans IA, les modules importés par un fichier coché et non lus (imports relatifs des fichiers JavaScript et TypeScript), vérifiés à la même version : non coché — **Ajouter à la sélection** —, présent dans le dépôt mais non lu — **Ajouter à la sélection** le lit à la même version, dans les plafonds de lecture, ou dit pourquoi c’est impossible —, absent du dépôt, ou existence non vérifiée. Un écart que l’assistant rattache à une question de l’exigence (Q-nn) dit **question Q-nn**, jamais « règle absente » ; une citation n’est jamais recalée sur une ligne de déclaration (`import`, `type`, `interface`). Le code cité entre backticks est contrôlé avec tolérance : une citation de l’exigence, ou un fragment sans caractère de code, n’est pas contrôlé ; `==` et `===`, guillemets droits et typographiques se valent, `…` vaut « n’importe quoi » ; le fragment est cherché dans tout le fichier cité, puis dans les autres fichiers lus. Quand un écart est écarté pour code introuvable, le fragment manquant est montré. Une proposition qu’un commentaire de ses lignes citées — ou le texte d’une autre de ses citations, une ligne de README par exemple (« aucun verrou contre deux enregistrements simultanés ») — dément (`// Pas de verrou : …`) est écartée. Une « règle issue du code » que le code cité dément n’est jamais montrée comme issue du code : elle est écartée quand elle refuse ce qu’une ligne citée accepte (« le préfixe `L-` n’est pas accepté » contre `// accepte aussi le préfixe « L- »`) ou quand ses nombres ne sont pas les bornes du code cité (« 8 à 20 » contre `phone.length < 10`). Quand un écran lu borne un champ plus strictement que le validateur lu (`maxLength 20` contre `> 30`), Studio pose l’écart lui-même : au-delà de la borne de l’écran, la règle ne se teste que par l’API. **Question au PO** ajoute une question de priorité importante. L’assistant est averti des dépendances non lues et ne doit rien en supposer.

**Un échec garde le résultat.** Si une confrontation échoue ou est annulée, le résultat précédent reste affiché (avec son heure) sous le message, et les questions déjà ajoutées le restent.

**Ce que vous faites d’un écart.** **Question au PO** l’ajoute à l’évaluation de l’exigence (source « code », priorité fixée par Studio) ; **Copier** le met dans le presse-papiers ; **Ignorer** le met de côté. Rien n’est écrit dans l’US ni dans Azure DevOps.

**Propositions sur le modèle de test.** Dans Conception, **Proposer au modèle** envoie une proposition (une partition, une valeur, une règle numérotée C-n, une référence corrigée) à l’étape du modèle, où vous acceptez ou refusez chacune. La conception est ensuite recalculée par Studio : éléments de couverture nouveaux, cas nouveaux à rédiger par le parcours habituel, cas existants à revoir (jamais modifiés). Les cas issus du code portent le tag « source:code ».
