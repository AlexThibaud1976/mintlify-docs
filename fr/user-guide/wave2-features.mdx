La vague 2 ouvre TestPulse Studio aux équipes automation et consolide le reporting multi-applications.

## Importer des résultats JUnit / NUnit / xUnit {#import-junit}

Ouvrez l'onglet **Import**, puis glissez-déposez (ou choisissez) un fichier `.xml` produit par Cypress, Playwright, Surefire/Maven, NUnit 3 ou xUnit 2. Le format est détecté automatiquement depuis le tag racine. Les résultats analysés sont prévisualisés dans une table (nom, résultat, durée, mappé). Le mapping vers les cas ADO se fait par nom (contains insensible à la casse) ; les lignes non mappées proposent une liste manuelle. Choisissez le plan ADO cible, puis cliquez sur **Importer** — un rapport est sauvegardé dans l'Historique avec un badge **[AUTO]**. L'analyse est purement côté client (aucun appel réseau).

## Rapports consolidés multi-plans {#multi-plan}

Activez le **Mode multi-plans** dans le sélecteur pour cocher plusieurs plans. L'unique bouton **Générer** produit un rapport consolidé : **métriques globales** (pass rate = total passés / total exécutés) plus une section **Détail par plan** — affichée **à l'écran** comme dans **chaque export** — donnant pour chaque plan son total, son taux de réussite, son taux d'exécution et ses compteurs passés/échoués/bloqués/non exécutés, ainsi qu'une colonne **Plan** dans la table des résultats. Le consolidé dédoublonne les cas présents dans plusieurs plans (le résultat le plus récent gagne) tandis que les chiffres par plan sont bruts ; lorsqu'un recouvrement est détecté, une note explique pourquoi la somme des totaux par plan peut dépasser le total consolidé. PDF, HTML, Word et Excel supportent tous le format consolidé. Une alerte non bloquante apparaît au-delà de 3 plans. Le comportement single-plan est inchangé.

## Échecs sans défaut {#failures-without-defect}

Avec la source de bugs par défaut (bugs des exécutions du plan), un cas de test en échec est un échec sans défaut quand **aucun bug n’est rattaché à son résultat** dans les runs lus. TestPulse Studio signale chaque cas de test dont le dernier résultat est **Failed** mais qui n'a **aucun bug lié** (avec la source *Liens des cas de test et des User Stories* : relation `TestedBy`, quel que soit l'état du bug — même Closed). Le signal est en lecture seule et n'ajoute **aucun appel API** (il réutilise la requête de traçabilité). Il apparaît comme une section dédiée **Échecs sans défaut** dans le rapport (chaque cas de test est un lien cliquable, avec les configurations en échec et un bouton **Ouvrir un bug** qui ouvre le formulaire de création de bug ADO natif, pré-rempli — jamais une écriture API), et comme critère **optionnel** du Quality Gate (désactivé par défaut : une fois activé et si le compteur est &gt; 0, le verdict passe **NO-GO** ; le grade A–E n'est jamais plafonné par ce critère). La détection est par point de test (config-aware) mais le compteur de tête est le nombre de cas de test distincts ; un bug lié au niveau du cas de test couvre toutes ses configurations. Exports : section complète en PDF/HTML, compteur sur une ligne en Word/Excel. Les rapports historiques sans le champ se dégradent proprement (compteur 0, section masquée).

## Couverture d’exigences historique {#historical-coverage}

L’onglet Tendances affiche désormais un **5ᵉ graphique « Couverture des exigences »** qui trace l’évolution du taux de couverture rapport après rapport pour un plan, plus une **colonne Couverture** dans la table comparative. Il est dérivé gratuitement de l’historique déjà sauvegardé — **aucun appel réseau, aucun stockage supplémentaire**. Un rapport dont la couverture n’est **pas mesurable** (rapports antérieurs, ou aucune exigence en périmètre) est un **trou** (un creux dans la courbe, « — » dans la table), jamais un 0 % trompeur. Par plan uniquement ; la courbe commence au premier rapport ayant mesuré la couverture et est bornée par la rétention de l’historique.

## Points de vigilance {#vigilance}

Un encart **Points de vigilance** apparaît juste sous le badge qualité (et en cartouche dans le PDF, près du badge de synthèse) pour **nommer** ce qui pèse déjà sur le verdict, au lieu de le laisser en compteurs. Trois groupes, chacun avec son compteur et affiché seulement s'il est non vide : **bugs bloquants ouverts** (`#id · sévérité · titre`), **exigences en périmètre sans test** (`#id · titre · état`), et rappel des **US in-scope non exécutées**. Chaque entrée est un lien cliquable vers le work item. « Bloquant » repose sur une **définition unique partagée** — la règle exacte de (bug ouvert de sévérité `1 - Critical` ou `2 - High`) — de sorte que l'encart et le cap du badge comptent toujours les mêmes bugs. Les exigences non couvertes sont **dérivées gratuitement au build** à partir des mêmes ensembles que le taux de couverture (périmètre suite-based : exigences rattachées au plan via les suites d'exigences), avec la garantie qu'une couverture à 100 % donne une liste vide. C'est de la **mise en exergue de données déjà calculées** : aucune nouvelle métrique, le score A–E est inchangé, sans appel réseau. L'encart est masqué si le score est « non évalué », affiche un état vide explicite quand rien n'est signalé, et tolère les rapports historiques sans le nouveau champ.

**Honnête par conception** : l'encart ne surveille que ces trois signaux, donc son état vide les nomme précisément (« aucun bug bloquant, exigence non couverte ni US non exécutée ») au lieu de laisser croire que toute la release est saine. Quand les trois signaux sont vides **et que le verdict est NO-GO**, l'encart **n'affiche pas** de ✓ vert — il reste neutre, nomme la vraie raison du NO-GO (le premier plafond du détail du score, ou le score et le barème) et renvoie au détail Qualité. Un ✓ vert n'apparaît que sur un **GO** franc.

## Décision GO/NO-GO auditée & bugs ouverts en tête {#decision-override}

Deux ajouts complémentaires, tous deux **opt-in/additifs** — un rapport sans décision ni bug ouvert est rendu **exactement** comme avant. **(A) Override de décision audité.** Le verdict GO/NO-GO est calculé par le moteur et reste, par conception, déterministe. L'override permet à un responsable de release d'y **superposer une décision humaine** — **sans jamais modifier le calcul**. Un administrateur du projet l'active via **« Autoriser l'override de décision GO/NO-GO »**, dans le barème qualité de *Paramètres du projet › Extensions › TestPulse Studio › Profils de configuration* (niveau projet, **OFF par défaut**) ; le profil **Strict** le laisse désactivé (clients régulés protégés). Une fois activé, un petit contrôle **Décision de release** apparaît à côté du badge qualité : garder *Suivre le calcul*, ou forcer **GO**/**NO-GO**. Quand votre décision **diffère** du calcul, une **justification est obligatoire** (la génération/sauvegarde est bloquée tant qu'elle est vide), et l'**auteur** et l'**horodatage** sont capturés. Le rapport affiche alors **calculé → décidé** côte à côte — en-tête web, PDF et export Word — avec la justification, l'auteur et la date. Un **GO manuel franchissant un plancher dur** (bug bloquant ouvert, US in-scope non testée, échec sans défaut…) est **signalé en rouge avec les raisons exactes** (icône **et** texte, jamais la couleur seule) ; une différence **sans** plancher dur est montrée comme une déviation « souple », au ton informatif. Le **grade A–E reste toujours celui du calcul** — seul le verdict GO/NO-GO est superposé, et la décision voyage avec le rapport (sauvegardée/restaurée dans l'historique). Aucun nouvel appel ADO, scope ni dépendance : l'auteur vient de votre identité in-page, le reste de données déjà chargées. **(B) Bugs ouverts en tête.** Un bloc concis **Bugs ouverts** apparaît désormais **en tête de rapport** (PDF, HTML, Word), juste après l'en-tête qualité et avant les sections détaillées. Il liste **tous** les bugs **ouverts** (état ∈ vos états « ouvert ») triés **sévérité (Critical→Low), puis priorité, puis date de création (la plus récente d’abord), puis id**, avec la sévérité, la priorité, le `#id` (lien), le titre, l'état et l'assigné. Il s'affiche **dès qu'il existe au moins un bug ouvert**, indépendamment du toggle de section « bugs liés », et reste **cohérent en comptage** avec l'encart Points de vigilance (qui ne liste que les bugs *bloquants* ouverts) — pas d'encart dupliqué, pas de chiffres contradictoires.

## Profils de barème & pondération risk-based {#quality-profiles-weighting}

Deux mécanismes séparés, jamais fondus, par-dessus le score qualité. **(A) Profils de barème** — dans l’administration du projet (*Profils de configuration › Défaut du projet › Seuils et qualité*, réservé aux administrateurs du projet), un barème est choisi **au niveau projet** : **Strict** (release régulée), **Standard** (le barème actuel, défaut) ou **Rodage** (projet en démarrage). Les membres le lisent dans *Mes préférences › Seuils et calculs*. Il est stocké au scope projet (Extension Data `Default`, comme le partage de rapport) pour que tout le monde note un rapport à l’identique. L’ajustement est **borné** (seuil GO 50–95, couverture minimale, poids des composantes forcés à 100, seuils A&gt;B&gt;C&gt;D) ; toute valeur hors preset devient un barème **Personnalisé**. Les invariants non-désactivables tiennent toujours (un bug bloquant ouvert ⇒ NO-GO ; aucun test exécuté ⇒ « non évalué »). Le barème actif est capturé dans le rapport ; les rapports historiques sans barème reviennent à Standard — identique à aujourd’hui. **(B) Pondération risk-based** — un toggle optionnel (orthogonal au profil) qui affiche une **confiance pondérée** à côté du badge dans le rapport et le PDF. Elle pondère exécution et couverture par l’**importance** de ce qui manque : **priorité** des cas de test, **risque** et **story points** des US, via des **paliers additifs** transparents (ex. P1=8…P4=1) — **jamais** une multiplication. Le score A–E à plat n’est **jamais** modifié (toggle off ou Standard ⇒ la sortie exacte). Honnête par conception : une dimension dont la donnée est **absente ou uniforme** s’auto-désactive et le dit — aucune confiance fabriquée ; si toutes sont creuses la pondération est inactive. Les champs work item (priorité, risque, story points) sont lus depuis les batches **existants** — **aucun appel ADO supplémentaire**.

## Notifications Microsoft Teams / Slack {#notifications}

Dans *Mes préférences › Notifications et envois*, ajoutez jusqu'à 3 canaux de publication en tout (nom, Microsoft Teams ou Slack, une adresse de webhook en `https`, **masquée** à l'écran et jamais affichée en entier) ; les canaux que le projet impose pour le plan viennent en tête, en lecture. **Envoyer un test** envoie un message d'exemple, sur chaque canal. Après génération, cliquez sur **Notifier** : il propose d'abord les canaux du projet pour le plan, puis les vôtres, et pousse les KPIs vers ceux que vous cochez (Adaptive Card pour Microsoft Teams, Block Kit pour Slack). Limitation CORS on-premise : si le navigateur bloque la requête, le message est proposé à copier-coller.

## Rapports programmés {#scheduling}

Dans *Mes préférences › Notifications et envois*, sous **Rappels de génération**, programmez un plan (optionnellement une vue sauvegardée) avec une fréquence hebdomadaire / bimensuelle / mensuelle ; les rappels que le projet impose viennent en tête, en lecture. Lorsqu'un rapport est en retard, une bannière de rappel apparaît **au démarrage** avec un bouton **Générer maintenant** (charge la vue sauvegardée et génère ; le rapport porte la date de son exécution, sans bandeau — personne n’est devant l’écran). Note : aucun serveur n’envoie ces rappels — **ils n’apparaissent que lorsque TestPulse Studio est ouvert**.

## Annotations par cas de test {#annotations}

Sur un rapport généré, survolez une ligne de résultats et cliquez sur l'icône **crayon** pour ajouter une annotation libre (500 caractères max), ex. « faux négatif — environnement instable ». Les annotations sont sauvegardées dans l'Historique et apparaissent dans la colonne **Commentaire** des exports PDF, HTML, Word et Excel. Note : les annotations ne sont persistées que pour les rapports présents dans l'Historique.

## Sélection en cascade & persistance du plan {#cascade-selection}

Cocher une suite parente sélectionne désormais **toutes ses sous-suites** à tout niveau ; la décocher les retire toutes. Une parente dont les descendants ne sont que partiellement sélectionnés affiche une case **indéterminée** (tri-state). La sélection reste au niveau suite (pas de sélection de cas individuel). Le plan sélectionné et ses suites cochées sont désormais **préservés au changement d'onglet** dans une session — aller sur l'Historique puis revenir ne réinitialise plus la sélection. Si le plan mémorisé disparaît, un message non bloquant invite à en choisir un autre.
