**Où et qui.** La grille de test se règle dans **Paramètres du projet › Extensions › TestPulse Studio › Grille de test**, et elle est **réservée aux administrateurs du projet**. Elle vit dans la configuration du projet : adoptez d'abord une base dans *Profils de configuration* — d'ici là, la grille livrée s'applique et se lit seulement. Comme toute page de l'administration, une modification reste un brouillon jusqu'à **Enregistrer**, dans le bandeau en tête.

**Trois axes, nommés comme le syllabus ISTQB Fondation.** La page s'ouvre sur un bandeau, **Comment Studio range un test**, puis montre une liste par axe et, à côté, le **détail de l'entrée choisie**. Les **niveaux de test** — *Tests de composants*, *Tests d'intégration de composants*, *Tests système*, *Tests d'intégration du système*, *Tests d'acceptation* — sont fermés : ils se renomment et voient leurs règles modifiées, ils ne s'ajoutent ni ne se suppriment. Les **types de test** — *Tests fonctionnels* et les caractéristiques de qualité de l'ISO/IEC 25010 (*Efficacité de la performance*, *Compatibilité*, *Utilisabilité* avec *Accessibilité* sous elle, *Fiabilité*, *Sécurité*, *Maintenabilité*, *Portabilité*) — et les **objectifs transverses** — *Tests de confirmation*, *Tests de régression*, *Tests de maintenance* — s'étendent de vos propres entrées. Un test peut porter un niveau, plusieurs types et plusieurs objectifs.

**Pourquoi la régression n'est pas un type.** Les tests de régression sont un *objectif* — rejouer des tests après un changement — qui vaut pour des tests fonctionnels comme non fonctionnels, à tout niveau. C'est donc un objectif de la grille, pas un type. De même, la *recette (UAT)* est le **niveau** d'acceptation, et l'*intégration* le **niveau** d'intégration du système.

**Les techniques ne sont pas dans la grille.** Les cinq techniques de conception du syllabus — *Partitions d'équivalence*, *Analyse des valeurs limites*, *Test par tables de décisions*, *Test de transition d'état*, *Devinette d'erreur* — se choisissent en concevant des tests, elles ne se détectent pas dans un plan. Les anciens cas nominaux et négatifs étaient les partitions valides et invalides de l'équivalence : ils comptent désormais comme partitions d'équivalence.

**Attendu par défaut.** Seuls les *Tests fonctionnels* sont attendus par défaut dans la grille livrée. Une entrée livrée se renomme, se marque non attendue, reçoit une consigne de conception et voit ses règles modifiées ; elle ne se supprime pas.

**Comment Studio range un test.** Studio lit quatre informations d'un test : ses **tags**, le nom de sa **suite**, son **area path** et son **titre**. Pour chaque entrée, il essaie ses conditions dans cet ordre — tags, puis suite, area path, titre — et **la première qui correspond range le test dans l'entrée**. Chaque entrée dont une condition correspond est retenue : un test peut porter **plusieurs entrées d'un même axe**. Chaque entrée se reconnaît d'abord par son tag canonique, toujours actif — `niveau:<nom>` pour un niveau, `type:<nom>` pour un type, `objectif:<nom>` pour un objectif (par exemple `niveau:acceptance`, `type:performance`, `objectif:regression`) — puis par les libellés usuels en français et en anglais. Les tags déjà écrits sur les cas de test ne sont jamais réécrits : les anciens `type:uat`, `type:integration` et `type:regression` restent reconnus. Les comparaisons ignorent la casse et les accents ; *contient* cherche un **mot ou une expression entière**. La détection ne lit que ce qui est déjà chargé, sans appel supplémentaire.

**Le détail d'une entrée.** Son **Libellé** ; **Reconnu quand…** — la ligne 0 est le tag canonique, toujours actif, puis chaque condition avec sa phrase lisible (par exemple « → le titre du test contient le mot « injection » ») ; ↑ et ↓ déplacent une condition parmi celles de la même source, et un motif vide empêche l'enregistrement ; **Dans chaque plan** — attendu ou non, avec un minimum d'un test, de N tests ou de N % du plan : c'est le **défaut du projet**, qu'un profil peut changer dans *Profils de configuration › Grille attendue* ; **Consigne de conception**, envoyée au modèle quand il conçoit un test de ce type. **+ Ajouter un type** et **+ Ajouter un objectif** étendent la grille ; une entrée ajoutée se supprime par **Supprimer…**.

**Les tests sans type.** Un test qu'aucune condition ne reconnaît reste **sans type** : rien n'est deviné ; il est signalé, sans effet sur le verdict. Quand des règles portent sur l'area path mais qu'un area path n'a pas pu être lu, TestPulse Studio le dit plutôt que d'annoncer l'entrée absente.

**Tester la détection** — décrivez un test (titre, suite, area path, tags), ou prenez l'un des trois exemples, et voyez, axe par axe, où Studio le range et quelle condition a décidé. Le calcul se fait sur le brouillon, avec la détection réelle, sans appel à Azure DevOps.

**Les classements orphelins.** Quand des classements IA désignent encore un type retiré de la grille, une note en tête de page les compte — les rapports les ignorent — et **Purger…** les retire après confirmation.

**Le passage depuis l'ancien catalogue.** La première fois qu'un administrateur du projet ouvre l'administration, l'ancien catalogue passe à la grille **une fois**, par le même enregistrement que toute modification (une modification concurrente est détectée, rien n'est écrasé), et le passage est journalisé dans *Assistant IA › Journal et échecs*, sous *Grille*. Rien ne se perd : les libellés saisis, les règles ajoutées, les consignes de conception et ce que le projet attendait sont conservés. *Fonctionnel* reste un type ; *Non-régression* devient un objectif ; *Intégration* devient *Tests d'intégration du système* et *UAT* devient *Tests d'acceptation* (des niveaux) ; *Accessibilité*, *Performance* et *Sécurité* restent des types ; vos propres entrées deviennent des types. *Limites & non passants* est **retiré** — c'est une technique, l'*Analyse des valeurs limites* — et une note le dit ; les tests déjà classés sous lui restent lisibles comme « ancien type », jamais réécrits. Tant qu'un administrateur n'a pas ouvert l'administration, chaque membre **lit** déjà la grille par la même correspondance, sans rien écrire. Les classements IA validés passent à leur première lecture, par n'importe quel membre. Rien n'est écrit dans Azure DevOps.

**Ce qui est attendu, par profil.** *Profils de configuration › Grille attendue* : pour chaque entrée, par axe, *hériter*, *attendu* ou *non attendu*, et un minimum facultatif (N tests, ou N % du plan). Cela se résout comme tout autre réglage de profil — le profil du plan, puis le défaut du projet, puis ce que dit *Dans chaque plan* dans la grille.

**La section Conception.** Elle se règle pour tout le projet, sur la page *Exigences et conception* de l’administration (et non plus par profil de plan) ; elle règle ce qu'une génération de tests propose par défaut : le **niveau par défaut** (défaut du produit : *Tests système*), le **type par défaut** (défaut du produit : *Tests fonctionnels*), les **techniques autorisées** (par défaut, les cinq) et le **contrôle par le juge** (activé par défaut, mais seulement si un modèle de contrôle est réglé dans *Assistant IA › Connexion*). Elle se redéfinit en bloc, avec sa provenance, et se lit en lecture seule dans *Mes préférences › Règles du projet*.

**Jamais un facteur du verdict.** Un niveau, un type ou un objectif attendu absent, ou sous son minimum, devient un **point de vigilance** ; le verdict et le score qualité n'en dépendent pas. Voir [La grille de test dans le rapport](/fr/user-guide/test-types-report).
