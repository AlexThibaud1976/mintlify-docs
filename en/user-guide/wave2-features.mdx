Wave 2 opens TestPulse Studio to automation teams and consolidates reporting across applications.

## Importing JUnit / NUnit / xUnit results {#import-junit}

Open the **Import** tab, then drag-and-drop (or pick) an `.xml` file produced by Cypress, Playwright, Surefire/Maven, NUnit 3 or xUnit 2. The format is auto-detected from the root tag. Parsed results are previewed in a table (name, outcome, duration, mapped). Results are auto-mapped to ADO test cases by name (case-insensitive contains); unmapped rows offer a manual dropdown. Pick the target ADO plan, then click **Import** — a report is saved to History with an **[AUTO]** badge. Parsing is purely client-side (no network calls).

## Consolidated multi-plan reports {#multi-plan}

Toggle **Multi-plan mode** in the plan selector to pick several plans with checkboxes. The single **Generate** button produces one consolidated report: **global metrics** (pass rate = total passed / total executed) plus a **Per plan breakdown** section — shown both **on screen** and in **every export** — giving each plan its total, pass rate, execution rate and passed/failed/blocked/not-run counts, and a **Plan** column in the results table. The consolidated view de-duplicates test cases present in several plans (most recent result wins) while per-plan figures are raw; when an overlap is detected a short note explains why the per-plan totals may exceed the consolidated total. PDF, HTML, Word and Excel all support the consolidated format. A non-blocking warning appears beyond 3 plans. Single-plan behaviour is unchanged.

## Failures without defect {#failures-without-defect}

With the default bug source (bugs from the plan runs), a failed test case is a failure without defect when **no bug is attached to its result** in any run read. TestPulse Studio flags every test case whose latest result is **Failed** but which has **no linked bug** (with the *Test case and User Story links* source: relation `TestedBy`, any bug state — even Closed). The signal is read-only and adds **no API call** (it reuses the traceability query). It appears as a dedicated **Failures without defect** section in the report (each test case is a clickable link, with the failing configurations and an **Open a bug** button that navigates to the native ADO bug-creation form, pre-filled — never a write API), and as an **opt-in** Quality Gate criterion (off by default: when enabled and the count is &gt; 0 the verdict becomes **NO-GO**; the A–E grade is never capped by it). Detection is per test point (config-aware) but the headline counter is the number of distinct test cases; a bug linked at the test-case level covers all its configurations. Exports: full section in PDF/HTML, one-line counter in Word/Excel. Historical reports without the field degrade gracefully (counter 0, section hidden).

## Historical requirements coverage {#historical-coverage}

The Trends tab now shows a **5th chart, "Requirements coverage"**, tracking how the coverage rate evolves report after report for a plan, plus a **Coverage column** in the comparison table. It is derived for free from the already-saved history — **no network call, no extra storage**. A report where coverage is **not measurable** (older reports, or no requirement in scope) is a **gap** (a hole in the curve, "—" in the table), never a misleading 0 %. Per-plan only; the curve starts at the first report that measured coverage and is bounded by history retention.

## Watch points {#vigilance}

A **Watch points** panel appears right under the quality badge (and as a cartouche in the PDF, next to the synthesis badge) to **name** what already weighs on the verdict, instead of leaving it as counters. Three groups, each with its count and shown only when non-empty: **open blocking bugs** (`#id · severity · title`), **in-scope requirements without any test** (`#id · title · state`), and a reminder of **in-scope user stories not executed**. Each entry is a clickable link to the work item. "Blocking" uses a **single shared definition** — the exact rule (open bug with severity `1 - Critical` or `2 - High`) — so the panel and the badge cap always count the same bugs. Uncovered requirements are **derived for free at build time** from the same sets as the coverage rate (suite-based scope: requirements attached to the plan via requirement-based suites), guaranteeing that 100 % coverage means an empty list. This is **highlighting of already-computed data**: no new metric, the A–E score is unchanged, no extra network call. The panel is hidden when the score is "not evaluated", shows an explicit empty state when nothing is flagged, and tolerates historical reports without the new field.

**Honest by design**: the panel watches only these three signals, so its empty state names them precisely ("no blocking bug, uncovered requirement or unexecuted user story") rather than implying the whole release is clear. When the three signals are empty **and the verdict is NO-GO**, the panel does **not** show a green ✓ — it stays neutral, names the actual reason for the NO-GO (the first cap from the score breakdown, or the score and scale) and points you to the Quality details. A green ✓ only appears on a clear **GO**.

## Audited GO/NO-GO decision & open bugs on top {#decision-override}

Two complementary additions, both **opt-in/additive** — a report without a decision or without an open bug renders **exactly** as before. **(A) Audited decision override.** The GO/NO-GO verdict is computed by the engine and is, by design, deterministic. The override lets a release owner **overlay a human decision** on top of it — **without ever changing the computation**. A project administrator enables it with **"Allow GO/NO-GO decision override"**, in the quality scoring of *Project settings › Extensions › TestPulse Studio › Configuration profiles* (project-level, **off by default**); the **Strict** profile keeps it disabled (regulated customers protected). Once enabled, a small **Release decision** control sits next to the quality badge: keep *Follow the computation*, or force **GO**/**NO-GO**. When your decision **differs** from the computation a **justification is mandatory** (generation/save is blocked until it is filled), and the **author** and **timestamp** are captured. The report then shows **computed → decided** side by side — in the web header, the PDF and the Word export — with the justification, author and date. A manual **GO that crosses a hard floor** (open blocking bug, untested in-scope story, failure without a defect…) is **flagged in red with the exact reasons** (icon **and** text, never colour alone); a difference with **no** hard floor is shown as a "soft" deviation in an informative tone. The **A–E grade always stays the computed one** — only the GO/NO-GO verdict is overlaid, and the decision travels with the report (saved/restored in history). No new ADO call, scope or dependency: the author comes from your in-page identity, everything else from data already loaded. **(B) Open bugs on top.** A concise **Open bugs** block now appears **at the top of the report** (PDF, HTML, Word), right after the quality header and before the detailed sections. It lists every **open** bug (state ∈ your open-bug states) sorted **severity (Critical→Low), then priority, then creation date (newest first), then id**, with severity, priority, the bug `#id` (linked), title, state and assignee. It shows **whenever there is at least one open bug**, independently of the "linked bugs" section toggle, and stays **count-consistent** with the Watch points panel (which lists only the *blocking* open bugs) — no duplicated panel, no contradictory numbers.

## Scale profiles & risk-based weighting {#quality-profiles-weighting}

Two separate, never-merged mechanisms on top of the quality score. **(A) Scale profiles** — in the project administration (*Configuration profiles › Project default › Thresholds and quality*, reserved for project administrators), a **project-level** scale is chosen: **Strict** (regulated release), **Standard** (the current scale, default) or **Rodage** (a project getting started). Members read it in *My preferences › Thresholds and calculations*. It is stored at project scope (Extension Data `Default`, like report sharing) so everyone scores the same report identically. Tuning is **bounded** (GO threshold 50–95, minimum coverage, component weights forced to sum 100, A&gt;B&gt;C&gt;D thresholds); any off-preset value becomes a **Custom** scale. The non-disable-able invariants always hold (an open blocking bug ⇒ NO-GO; no executed test ⇒ "not evaluated"). The active scale is captured in the report; historical reports without it fall back to Standard — identical to today. **(B) Risk-based weighting** — an optional toggle (orthogonal to the profile) that shows a **weighted confidence** beside the badge in the report and the PDF. It weights execution and coverage by the **importance** of what is missing: test-case **priority**, US **risk** and **story points**, using transparent **additive tiers** (e.g. P1=8…P4=1) — **never** a multiplication. The flat A–E score is **never** altered (toggle off or Standard ⇒ the exact output). Honest by design: a dimension whose data is **absent or uniform** auto-disables and says so — no fabricated confidence; if all are hollow the weighting is inactive. The work-item fields (priority, risk, story points) are read from the **existing** batches — **no extra ADO call**.

## Microsoft Teams / Slack notifications {#notifications}

In *My preferences › Notifications and sending*, add up to 3 publishing channels in all (name, Microsoft Teams or Slack, a webhook address in `https`, **masked** on screen and never shown in full); the channels the project sets for the plan come first, read-only. **Send a test** sends a sample message, on every channel. After generating a report, click **Notify**: it offers the project’s channels for the plan first, then yours, and pushes the KPIs to the selected ones (Adaptive Card for Microsoft Teams, Block Kit for Slack). On-premise CORS limitation: if the browser blocks the request, the message is offered for copy-paste.

## Scheduled reports {#scheduling}

In *My preferences › Notifications and sending*, under **Generation reminders**, schedule a plan (optionally a saved view) with a weekly / biweekly / monthly frequency; the reminders the project sets come first, read-only. When a report becomes due, a reminder banner appears **at startup** with a **Generate now** button (loads the saved view and generates; the report carries the date of its run, with no banner — nobody is in front of the screen). Note: no server sends these reminders — **they only appear when TestPulse Studio is open**.

## Test case annotations {#annotations}

On a generated report, hover a results row and click the **pencil** icon to add a free-text annotation (max 500 characters), e.g. "false negative — unstable environment". Annotations are saved to History and appear in the **Comment** column of PDF, HTML, Word and Excel exports. Note: annotations are only persisted for reports stored in History.

## Cascade suite selection & plan persistence {#cascade-selection}

Checking a parent suite now selects **all its sub-suites** at any depth; unchecking removes them all. A parent whose descendants are only partly selected shows an **indeterminate** (tri-state) checkbox. Selection stays at the suite level (no individual test-case selection). The selected plan and its checked suites are now **preserved across tab switches** within a session — switching to History and back no longer resets your selection. If the memorized plan disappears, a non-blocking message prompts you to pick another.
