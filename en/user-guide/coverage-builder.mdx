The **Coverage** tab starts from **requirements** (not a plan) and answers: *what do I need to test the regression of these features?* It surfaces the existing tests linked to those requirements (`TestedBy`), flags the **gaps** (requirements with no test), previews a regression plan, and — after explicit confirmation — can **create** that plan in ADO. Read first, write later: you get value (analysis + exportable plan spec) **before** paying the write cost. The **Configuration panel** switch folds the requirement selection and options away so the matrix uses the full width; the number of requirements and the active options stay visible as chips, and **Analyze coverage** stays in the bar — the only one: it is the main action before the analysis; after it, the selection folds once (open it again whenever you like) and the main action becomes **Create the plan in ADO** (plan name, exports and target under *Creation options*). The table reads Requirement · State · Tests (· Plans); the assessment and the linked code show as a one-line pill, the detail per row.

## Selecting requirements & reading coverage {#coverage-select}

Select requirements by **area path**, **iteration**, a **WIQL query**, or a list of **IDs** — you start from the features to cover, not from an existing plan. TestPulse Studio then resolves, for each requirement, the test cases linked via `TestedBy` (the same link primitive used elsewhere, just in the requirement→test direction) and classifies each one **covered** (has at least one linked test) or **gap** (no linked test). The composition uses the **link graph only** — no outcomes, points or runs are read, and no new permission is required. Metric cards summarise total / covered / gaps / linked tests. **100 % gaps is a valid result** (a plan made entirely of empty suites, ready to fill), never an error.

## The optional "covered but unplanned" state {#coverage-unplanned}

A third state — *covered but unplanned* (a test exists for the requirement but isn’t in any test plan, so you’d want to reuse it rather than rewrite it) — is available behind an **opt-in "Planning scan" toggle, off by default**. It is more expensive: it must enumerate plans → suites → test cases to know whether each test is already planned. That cost is signalled, and the state is **never shown unless a real scan was performed**. Without the toggle, the core stays a clean two states (covered / gap).

## Plan preview & read-only export {#coverage-export}

From the coverage result, TestPulse Studio builds a **plan spec**: one requirement-based suite per selected requirement, each with its expected (auto-populated) test cases and a gap flag. A **preview** shows what would be created (e.g. "9 requirement-based suites, 34 test cases"). The **"Export spec"** button is **always available and needs no permission** — it serialises the spec to **JSON, Markdown or CSV** so a quality lead without write rights keeps the full read value (build the plan by hand, or hand it off). The export reflects exactly the preview.

## Creating the plan in ADO (write — permission + confirmation) {#coverage-create}

**Plan creation is the first feature of TestPulse Studio that writes to Azure DevOps.** From the preview, **"Create plan in ADO"** opens a **confirmation dialog** recapping exactly what will be written (N requirement-based suites, M auto-populated tests, K empty gap suites). **Nothing is written before you confirm.** On confirm, TestPulse Studio creates the plan and one requirement-based suite per requirement — ADO **auto-populates** the covered ones from `TestedBy` and leaves the gaps **empty** (living scaffolding: the day a test is written and linked, it shows up by itself). It is **creation only** — it never modifies or deletes any existing plan, suite or test; a **name collision warns** instead of overwriting; a **partial failure reports** exactly what was created. Creating the plan uses the **`vso.test_write`** scope, already declared by TestPulse Studio and granted when the extension is installed; it writes only after your click, with your rights.

## Choosing the area path & iteration — and the “permission ≠ scope” 403 {#coverage-target}

Before creating, the preview lets you **pick the area path** (and, optionally, the **iteration**) the new plan will live under. This is the field that fixes the most common creation failure: a **403 — *you do not have the appropriate permissions to manage test plans under this area path***. Azure DevOps grants the *Manage test plans* permission **per area path**; if you don’t choose one, the plan is created under the **project root**, where you may not hold that right. Pick an area where you do, and creation succeeds. Leave both empty and the behaviour is unchanged (project root, as before); the lists are read from the project’s classification nodes using the **existing `vso.work` scope** — no new permission — and if they can’t be read you can still type a path by hand. **This 403 is not a scope problem.** `vso.test_write` is already granted; the error is an **area-path ACL**. TestPulse Studio now says so honestly: a permission-related 403 points you to *Manage test plans on the chosen area path* (ask your administrator), and the “add the scope” message appears **only** when the scope is genuinely the cause (e.g. a 401).

## Assessing coverage *depth* — "is it well covered?" {#coverage-depth}

Plain coverage is **structural**: a requirement with ≥1 linked test is "covered", even if a single trivial smoke test stands in for five acceptance criteria — false confidence. Turn on the opt-in **"Assess coverage depth"** toggle (off by default; off ⇒ the Coverage tab is strictly unchanged) and, after *Analyze coverage*, TestPulse Studio adds a **Depth** column with a per-requirement band:
- **Well covered** — the tests appear to cover the acceptance criteria.
- **Partial** — criteria or paths are probably missing.
- **Shallow** — too few tests, or tests without steps.
- **Gap** — no linked test.
- **Underspecified** — no (or few) acceptance criteria to assess against.

Expand a row to see the **findings** (the reasons, with ADO links) and concrete **improvement axes** ("add a negative test for…", "flesh out the N tests without steps", "confirm a test covers *X*"). The analysis is **100% deterministic and AI-free** — it counts acceptance criteria, measures step depth, looks for negative/edge keywords (**FR + EN**), checks term overlap and execution. It is **advisory only**: it never blocks anything, never feeds the quality score / GO-NO-GO, never changes an outcome. The wording is deliberately cautious ("possible", "apparent") — it is a "review this" signal; **you** decide. It is **read-only** (the test content is read via the existing batch primitive — no new ADO call or scope) and degrades gracefully per requirement (a test with no steps still counts; no acceptance criteria ⇒ *Underspecified*, never an invented verdict).

## Improvement axes proposed by the AI {#coverage-axes}

After **Analyze coverage**, the **Improvement axes** panel below the table can **propose axes** with the AI assistant. The AI only comments on the analysis already computed: it recomputes nothing and writes nothing. Each axis has a priority (1 to 3), a short justification, the requirements it is about (click one to reach its row) and **one** action: **Design the tests** (opens Conception on that requirement, the missing techniques pre-checked), **Show the unplanned tests** (filters the table; « Run the planning scan » when the scan was not done) or **Compare duplicates** (opens the cited tests in Azure DevOps). The header says which model proposed the axes and when, with an AI label.

**Guard-rails.** An axis citing a requirement outside the selection is discarded and counted; a duplicates axis needs at least two tests that belong to the analysis. At most **40 requirements** are sent, the first ones by priority — the panel says so. Requirement descriptions and acceptance criteria are sent only when the « requirement text » category is checked in the project administration, *AI assistant › Functions and data*. If the analysis or the selection changes, the axes are greyed out (« analysis changed ») until you propose new ones. Nothing is stored.

**Closing a gap.** From Conception, once the cases are written, **Back to coverage and analyse again** returns to this tab with the same selection and runs the analysis once.

## Test coverage signal on the work item {#wit-coverage-signal}

TestPulse Studio also surfaces coverage **where PO and devs already work — on the work item itself**. Open a User Story / PBI and a dedicated **“Couverture” tab** appears on the form (a read-only contribution, isolated from the hub — the rest of TestPulse Studio is unchanged). The tab is **auto-placed** and **mounted on click**, so **nothing is read until you open it** — the card stays fast. On opening, it renders an **instant headline**: two cheap pills — **Coverage** (`Covered (N)` / `Not covered`, from the `TestedBy` links) and **Depth** (`Well / Partial / Shallow / Gap / Underspecified`, from the same analyzer on acceptance criteria + description + linked-test content) — with **no test-result reads**. Then the detail **loads automatically** (no more manual expand): a **depth-analysis** block (the findings, e.g. *“no testable criteria detected”* for Underspecified), a **numeric summary** (`failing` / `bugs` / `failing-no-defect` counts + last executed), and a **tests table** with the **linked tests’ latest pass/fail** (the most recent outcome aggregated per test case, failures first), the **bug behind each failing test** (#id, severity, state, assignee), and the **failing tests with no defect logged** (reusing the logic). Everything is **read-only and live (Model A)** — computed directly from the story, **independent of any published TestPulse Studio report**. It **reuses** the existing engines (depth, traceability status, failure-without-defect) rather than reimplementing them, uses only the **already-granted** `vso.work` + `vso.test` scopes (**no new scope, no new dependency, never any write**), and **never reads comments**. The pass/fail comes from resolving each test case to its plan/suite (`testplan/suites?testCaseId`, api-version 7.1, confirmed on Server 2022.1) → the existing points endpoint → a “latest” aggregation; the bugs from the existing WIQL test-case→bug query. There is a **per-work-item cache** (revisiting a card does not re-fetch), and a short timeout degrades to a quiet *“coverage unavailable”* — it never throws an error onto the card. A story with **no linked test** shows a neutral *No linked test cases* (and skips the fetch entirely); vague/empty acceptance criteria show *Underspecified* honestly rather than an invented score. *(The tab appears on every work-item type; where coverage does not apply — a Bug, Task or Test Case — the neutral state covers it cleanly.)*

The tab honours **both languages**: it opens in your **auto-detected** locale and carries its **own FR/EN switch** (top-right), remembered **locally in the browser** with **no ADO call**. Its presentation was **refreshed** — **two colour-framed verdict cards** (coverage, depth), each section in a **clearly framed card** with a coloured header icon, a **tiled** summary with coloured category icons, and a framed table with **outcome pills** and test-type tags (same data, clearer read; depth stays honest, never a fabricated score).

**Scope selector.** When a story spans **more than one test plan**, a **scope selector** appears above the detail: **“Latest (all plans)”** (the default — the most recent outcome across every plan, exactly as before) or **a specific test plan** (Xray-style). Pick a plan and the tab **masks the tests that aren’t in it** (an *“X of N in this plan”* line makes the masking explicit) and **re-scopes** the tested status, the failures, the failing-no-defect flag and the freshness **to that plan** — while **Coverage, Depth and the bug list stay plan-independent** (a bug binds to a test case, not a plan). Switching scope is **instant and in-memory** — **no new ADO call** (the per-plan results were already fetched when the tab opened) — and your choice is **remembered per work item** (locally, no ADO write), gracefully falling back to *Latest* if the remembered plan no longer applies.

**Execution-verdict banner.** The detail now leads with a colour-coded **execution verdict** — **Passed** (green), **Not OK** (red), **Not Run** (grey) or **Not covered** (neutral) — so you read *does it pass?* at a glance, not just *is it covered?*. It’s a **pure reduction** of the tests already shown, with **strict precedence** (no “partial”): **any Failed ⇒ Not OK**; otherwise **any non-passed** (`Blocked`, `NotApplicable`, `NotExecuted`, `Inconclusive`, `None`) **⇒ Not Run**; **only 100% Passed ⇒ Passed**; **0 linked test / not covered ⇒ Not covered**. It respects the **scope selector** (it verdicts the *selected plan*) and **re-computes in memory** when you switch scope — **no new read**. Shown with **icon + label** (never colour alone; explicit colours robust in light and dark themes), it is a **distinct axis** from coverage and **never recolours the Coverage card** (“is it tested?” vs “does it pass?”).

**Navigability.** The tests table is now **sortable and rebound-able**. **Click any of the five column headers** — **#, Test, Outcome, Last run, Bug** — to sort, and click the same header again to **reverse** the direction (`aria-sort` reflects the active column). Outcome sorts via the **same rank** the default view uses (failures first, Passed last), Test by **name** (the `[tag]` prefix is ignored), Last run chronologically (never-run rows last). Your **sort is remembered per work item** (locally, no ADO write) and the **default order is unchanged**. Two **one-click jumps** are added: an **executed** row (a real run behind it) links from its **Last run** cell to the **test run** (`_testManagement/runs`), and when a **specific plan** is scoped a **“Run in Azure DevOps”** link sits by the scope selector, opening the plan’s **execute** view (`_testPlans/execute`). Both open in a **new tab** (`rel="noopener noreferrer"`) and are **portal navigations, not API calls** — the run id was **already read**, so there is **no new call, scope or dependency**; the links **degrade gracefully** when the host URL is unavailable.

**Coverage plan insights.** In the **Coverage builder**, with **Planning scan** on, a **Plans** column shows, per requirement, where its linked tests are planned — the plan name if unique, **“N plans”** if several, **“—”** for a gap (or when the scan is off). **Expand a row** to list each (plan, suite) couple with a **“Run in Azure DevOps”** deep-link to the plan’s **execute** view; a **lazy** read (only on expand, once per suite, degrades silently) fills in an **n/m run** progress. The plan detail is parsed from the **same** `suites?testCaseId` responses the scan already receives — **no extra API call at table load**. Every application plan link now targets **execute** (not the composition view) through a single shared URL builder.

**Config-correct resolution.** When the **same test case** covers **several sibling stories that only differ by test configuration** (a field team’s recurring pattern: one shared test case, one requirement-based suite per country/config — e.g. QUAL_IT / QUAL_SG / QUAL_KR), the tab used to show the **most recent outcome across every config**, so an Italy story could display a Singapore run by mistake. It now **resolves per test-point**: a story with a **requirement-based suite** (`suiteType="RequirementTestSuite"`, matching this story) restricts the “latest” to **its own configuration’s results** before picking the most recent — a story without one keeps the previous “latest overall” behaviour, unchanged. This reuses data the tab **already reads** (the point reader and `testplan/suites` responses expose `suiteId`, `resultId`, `configurationId/Name` — they were simply discarded before); **no new API call**. Two links get more precise as a result: the **run link** now points to the **exact result** (`&resultId=`) when the probe confirms it is populated (otherwise the link degrades to the run without a fabricated result id — never a hard-coded placeholder), and each row can open the **exact executed suite** (`_testPlans/execute` with its `suiteId`) instead of a **blank plan page**. The scope selector’s plan labels read **“&#123;plan&#125; · &#123;config&#125;”** when a configuration is known, unchanged otherwise.

**What changed since the last run.** The “Modified after last run” badge said a story had changed but not **what** changed. It now carries a **“Show detail”** button: expanding it triggers **one lazy read** (never on page load, only on first expand, then cached — collapsing and re-expanding never re-fetches) of the story’s revision history, collapsed **cumulatively** from the run date onward (several edits since the run are merged into one before/after, not just the latest edit). Only **business fields** are listed — Title, Acceptance criteria, Description, State, Priority, Iteration, Tags — system bookkeeping fields (Rev, Watermark, ChangedDate…) are filtered out. Scalar fields (State, Priority…) show a plain **before → after**; rich fields (Acceptance criteria, Description) get a small **home-made word diff** (no library) that **highlights the added wording**, with a plain side-by-side fallback if the HTML is too irregular to diff meaningfully. A change to Acceptance criteria or Description carries a **“feeds depth analysis”** badge, since those are exactly the fields the depth analyzer reads. A separate block lists **attachments added or removed** since the run (absent entirely when there is none — never an empty placeholder). Read-only, one new endpoint (`workItems/{id}/updates`, already covered by the existing `vso.work` scope), opt-in only.
