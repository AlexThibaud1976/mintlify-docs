Reassign the **tester** or the **configuration** of a whole test plan in one pass, from a **Bulk reassignment** tab. Azure DevOps can assign testers on a single suite, but the action does not cascade into child suites, so a plan of 172 suites means opening up to 172 of them. CSV import and the bulk-edit grid cannot reach these two properties at all: they belong to the **test point**, not to the Test Case work item.

The tab runs in five steps — **scope, inventory, operation, review, result**.

- **Scope** — one plan, or up to ten at once. Search the plan list by name, iteration or exact identifier; filtering hides plans without ever deselecting them, and the counter keeps showing the real total.
- **Inventory** — testers and configurations side by side, sorted by volume, each row showing its point count, how many already carry an execution result, and its share of the scope. Anything under 2 % of the points is marked residual, and **Unassigned** is a row of its own. Nothing is cached: the inventory is rebuilt on every analysis and carries the timestamp it was read at.
- **Operation** — three modes: replace one or more values with another, apply to the whole scope, or apply to a suite and all its child suites. What you replace **from** is the inventory of what the scope really carries; what you replace **towards** is not. Any configuration defined in the project can be the destination, including one no point carries yet — it shows `0` points and says in words that it is absent from the scope. One marked **inactive** in the project stays selectable too, says so in words, and sits at the end of the list behind everything still active. The destination tester is resolved against the identities of the organisation: type from three characters, pick from the list, and the tab keeps the identity rather than the text typed — reassigning a point requires the identity itself, so an unresolved name can never be validated as a destination. Testers already in the scope are offered straight away, without typing, and **Unassigned** stays available. Where the project configuration catalogue or identity search cannot be read — both can be restricted on Azure DevOps Server — the screen says so and falls back to what the scope carries. The suite picker is a tree with search, per-node and global expand/collapse, and the sub-suite and point counts of each subtree. A suite with no point of its own still appears as a branch so its children stay reachable; one whose entire subtree is empty is shown disabled.
- **Review** — points affected, suites touched, points already run, cases skipped, and the estimated number of API calls, plus the exact endpoint that will be called. You choose explicitly what happens to points that already carry a result, and can export the prior state as CSV.
- **Result** — how many points were reassigned out of how many, the duration, and every failure with its HTTP status and a plain-language cause. A retry button replays **only** the failures. Starting another reassignment takes you back to the **Scope** step, with nothing pre-selected and the plan list read again — the operation just applied made the previous inventory wrong, and a plan created or renamed meanwhile shows up as it is now. Replaying failed points brings you back the same way.

**Changing a tester and changing a configuration are not the same operation.** Changing the tester keeps the test point and its execution result attached — it is not destructive. Changing the configuration rewrites the test case's assignments, which Azure DevOps may implement by destroying the point and recreating it, taking its execution result with it. The two carry different warnings throughout, and the *include points already run* choice reads *the result stays attached to the point* for the tester against *the result will be lost* for the configuration. A test case that already carries the destination configuration is **skipped and listed**, never merged — merging would delete one of its assignments.

**The operation cannot be undone.** Azure DevOps offers no undo and TestPulse Studio keeps no prior state, so the CSV export of the review screen is the trace to keep. A partial failure is a valid outcome, not a corrupted one: nothing is rolled back, and the points already reassigned stay reassigned.
