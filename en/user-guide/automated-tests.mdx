**Where.** Step 5 **Automate** of **Design**, and the **Automated tests** section of the **Exigence** tab. The **Automated tests** function must be on (**AI assistant › Functions and data**).

**What you choose.** Manual test cases of the requirement — linked in Azure DevOps (Tested By), or designed in this session and written (step 4) —, one of the 8 framework · language combinations (Playwright · TypeScript by default, Selenium v4 · Java (JUnit 5), Cypress · JavaScript, Playwright · Python, Playwright · C# (.NET, NUnit), Cucumber · JavaScript, Cucumber · Java, Cucumber (pytest-bdd) · Python), and the code read at step 0 (**Read the code**). The last combination is remembered per project, for you. What is sent: the steps, expected results and data of the cases, the title of the story, and the code read if you attach it.

**What Studio does.** One automated test per manual test case, nothing more. The AI assistant writes the code of each manual step; Studio writes the files: folders and names, Page Object (or, for Cucumber, the `.feature` copied from the manual Gherkin case **without AI** and the step definitions), the data table from the iterations of the case, the test title `[TC <id>]` and the tag `@tc:<id>` (`tc_<id>` where the framework refuses “:”, as with pytest).

**Honest status.** Every selector, route or message must be cited in the code read (file, line ± 3). Anything the code read does not establish becomes a marker `À COMPLÉTER (TestPulse Studio) : <reason>` in the file, and the test is a **skeleton** (`test.fixme`, `@Disabled`, `it.skip`, `[Ignore]`, `pytest.mark.skip`, pending step); without marker it is **ready to review** — never “ready to run”: Studio runs nothing and gives no score. A light syntax check per language flags a broken file, which stays visible — and a test with a syntax error in one of its files (its own, the Page Object it calls, the step definitions) is never ready to review (marker “syntax error”). A step whose body has no statement (comments only, `pass`, a lone `return`) is not mapped. The assistant’s own markers (`# todo`, `// TODO`, `# FIXME`, “to complete”) become Studio markers; on a **complete** step — at least one citation, all found, no built value, no marker from Studio — the assistant’s remark becomes a **review note** (`Note de relecture (TestPulse Studio) : …`), shown but not blocking, and counted apart in the checks. With **Selenium**, actions are written inline (`driver.findElement(By…)`, `wait.until(…)`): no Page Object is suggested.

**Citations found in all the code read.** A citation that is not at the stated line ± 3 is looked for in the whole cited file, then in the other files read if it occurs only once there: it is **relocated** (`source : file:line (recalée)`). The forms of a test identifier are equivalent (`getByTestId("x")`, `[data-testid="x"]` and `data-testid="x"` in the code read), and a value built by a template of the code read (`error-<field>`) is found as a **built value**. A string written by the AI and cut by an apostrophe (“n’est” between single quotes) is repaired by Studio before the syntax check. With Cucumber, a case in steps + data is **not offered** (Gherkin required) — said in grey, never as a failure. A `.feature` uses one keyword language only, the one of most keywords of the scenario (the Gherkin keywords written by Design stay in English), and the precondition of the case becomes its `Background`.

**Home page, base URL, composed messages, identifiers.** Opening the home page (`/`, or the base URL with path `/` — `page.goto("/")`, `cy.visit("/")`, `driver.get(baseUrl)`, `browser.url("/")`) needs no citation: the test says **application root**, a source like a citation found; a citation of the AI that designates the root (“/”, `baseUrl`, `baseUrl + "/"`) is never converted into a marker. An absolute URL is accepted when its origin (host and port) is in a file read — `playwright.config.ts`, `vite.config.ts`, the server, the README —, otherwise it gets the marker “base URL to confirm”. A message built by the code from two values (`MSG-08 — <label>`, from a table of messages) is found when its parts are on one line of a file read and a template of that file joins them: **composed message**. A test identifier cited in the wrong file is found through its **declaration** (`data-testid=`, `id=`, `name=`) in a screen read; existing tests and documentation no longer make a value ambiguous. A precondition that uses parameters of the plan becomes the first step of the `Scenario Outline` instead of a `Background`.

**A selector is worth its declaration in the screen.** A test identifier is accepted only through its declaration in a screen read (`data-testid=`, `id=`, `name=`) or a template of a screen; a mention in the README or in an existing test is never a source — it is shown as a hint next to the marker “declaration not found in the screens read”. A text or message seen only in the documentation or a test is marked too. **Screen limits checked**: when a test types into a field a value that the screen would not take as is — a value of an iteration or a value written as a literal, whatever the framework (`fill`, `type`, `pressSequentially`, `sendKeys` inline or through the Page Object, `setValue`, and BDD step definitions, where the value is the one the step expression binds at each iteration); longer than its `maxLength` (the browser truncates it), shorter than its `minLength`, outside its `min` / `max` or its `pattern`, not one of the options of a list, or not a number for a numeric field —, Studio places the marker “value that cannot be entered as is (maxLength 20) — iteration 2” above that line, with two ways out: test the rule through the API, or correct the data of the case; the test is never ready to review, and the checks count these values. **Data of the case never ignored**: in an iterated test (loop over the data, `@ParameterizedTest`, `[TestCaseSource]`, `pytest.mark.parametrize`, `Examples`), a value typed as a literal that equals the value of a single iteration, or a column that changes from one iteration to the next and that the test never reads, gets the marker “value set by the test instead of the data "telephone" — the iterations do not vary”: the test would replay the same iteration; it stays a skeleton. The typed value is also found through its accessors (`data.telephone()`, `getTelephone()`, `row["telephone"]`, `row.get("telephone")`, `row.Telephone`, destructuring) for the screen-limit check. **A marker, never “ready”**: any Studio marker in a file of the test keeps it a skeleton, including in a step definition that no step binds or a Page Object method that no test calls; an AI citation that is not found is marked on the line that writes its value (`getByRole(…, { name: … })` included), and the “turned into markers” alert only lists values actually marked. When a test configuration is read (`testDir` of `playwright.config.ts`…), the generated Playwright · TypeScript files go under that test root; **Next steps** says which root was read.

**A drop-down list is selected, not typed.** When a test types a value into a `<select>` of the screen read (`fill`, `type`, `sendKeys`…), Studio places the marker “drop-down list filled like a text field” above that line: the option selection of the framework is expected (`selectOption`, `select`, `SelectOptionAsync`, `Select`). A keyed selector (`select[name="country"]`, `[data-testid="x"]`, `#id`, `By.id`, `By.name`) designates an element declared in the screen: a citation of that identifier alone, in the README for instance, is resolved to its declaration.

**One way of finding, whatever the combination.** A selector, text or route that the test uses is looked up by Studio itself in the code read, the same way as the citations of the AI: a test identifier through its declaration in a screen (`By.id` looks for an `id`, `By.name` for a `name`), a tag selector (`h1`) through the tag of the screen, a text or a route through its only occurrence outside tests and documentation — an expected text present in the screen and in a validator is taken from the screen. The result no longer depends on what the AI cited, nor on the combination. With Selenium, the screen limits are also checked when the element is kept in a variable before `sendKeys`, and `assertEquals` / `getText().contains` are expected texts. With pytest-bdd, a step definition only links the steps of its keyword (`@when` does not link a `Given` step), as pytest-bdd does; Cucumber ignores the keyword. A value typed by the test that is not in the data of the test case (`fill("Bureau")`) is noted in a comment above the line and counted, without a marker. On a step definitions file shared by several tests, the preview counter also says how many items count for the test shown.

**Page Object only when it has content.** The Page Object file is produced only when it has at least one method; otherwise no Page Object, and the tests neither import it nor declare `po`. A call `po.<method>(…)` to a method the AI assistant did not write is marked “Page Object method missing” and its step is not mapped. Generating in the Page Object the locators cited by the tests is planned, not done.

**Code shape checked.** A line written in another language than the one of the combination (`await page.…` in a Java or Python file, the JavaScript Playwright API — `getByTestId`, `toHaveText` — in a Python file and the Python one — `get_by_test_id` — in a Java, C# or JavaScript file, `public void` in a JavaScript file…) and a test declared inside a test (`it(…)` in the body of an `it`, `@Test` in a step) are marked, and their step is not mapped; another language is also listed with the syntax errors. In JavaScript and TypeScript, when the AI assistant wraps all the code of a test in its own test block (`it(…)`, `test(…)`, `describe(…)`, opened in the first step and closed in the last), Studio keeps only its body before any check, and lists the correction in **Journal and failures** (“kept, gaps marked”); a block that is never closed, or followed by other code, stays marked. A positive expected result (accepted, saved, created) is asked to be checked by the success witness the code read shows (`save-success`), with an explicit wait — the absence of an error only as a complement. For a refusal, the witness is the error message read (`error-street`, its MSG-xx text): a refusal step is never marked for lack of a positive witness. A sub-rule without its own witness (“the postal code respects the length rule”) is checked through what the code exposes — the global witness, the value kept, the absence of its error — with a review note, never an item to complete; an item to complete written by the AI assistant stays one. The AI assistant also receives the table of the elements declared in the screens read (selector, element, name, label, text shown, file, line). In Cucumber, a step expression that differs from the expected binding only in form (`{string}` for `{}`, apostrophe, final punctuation) is bound to the expected binding and counted in the checks; different words are never bound. A case missing from the AI assistant’s answer is asked again alone, once, with the methods and definitions already written (counted in the checks, and noted in **Log and failures**); it stays “without a usable result” only when the second answer misses it too. In a Python file, the JavaScript Playwright API is **translated by Studio** before any check (`getByTestId` → `get_by_test_id`, `{ name: x }` → `name=x`, `toBeVisible()` → `expect(…).to_be_visible()`, `await` and `;` removed), the line preceded by `# TestPulse Studio : API JS traduite en Python` and counted in the checks; what cannot be translated stays marked. A bare citation (`country`) found nowhere as text is looked for as a `data-testid`, `id` or `name` declared in a screen, and the text of options run together (`SuisseFranceBelgique`) as consecutive options of one `<select>`. In Cucumber, the AI assistant is given the expected binding of each step (an unquoted `<x>` is an anonymous parameter `{}`), and Studio checks the binding the way the framework matches it. The screen limits are also checked on the values passed to a method of the Page Object: the argument of rank *n* (or named) of the call is the value of the parameter of rank *n* (or of that name) of the method, whatever the language, even when the parameter bears the name of the field (`fill(phone)` in `getByTestId("phone")`); data passed to a method that does not read it, or that the method replaces with a fixed value, is marked “value set by the test instead of the data”. In BDD, a case that the AI assistant leaves out of its list of tests while its step definitions bind the scenario is not “without a usable result”: it is read from its definitions (noted in **Log and failures**).

**Preview.** File by file, the manual step next to its lines, markers highlighted; the counter above the code is the one of the file shown (“no item to complete in this file” on a Page Object without marker, even when the test is a skeleton). **Edit in place** recomputes the status; **Regenerate this test** asks the AI again for that case only. **Citations returned by the model** (folded block, without AI, nothing sent): every value the AI cited, the file and line it gave, and what the check made of it — found, relocated, built value, composed message, found for an expected text only, application root, or not found, with the reason (not in the code read, seen only in the documentation or a test, declaration not found in the screens read).

**What “ready to review” means.** It establishes that every selector, route and message of the test is found in the code you read, at the place shown, that the values of the iterations fit the limits of the screen read, and that the syntax check passed. It does not establish that the test passes: Studio runs nothing — no browser, no build, no test —, does not see the running application nor the code you did not read, and gives no score. Review it, run it in your pipeline, then link it.

**Delivery.** **Download the .zip archive** (built in the browser), or **create a pull request on a new branch** `testpulse-studio/tests-auto/us-<id>` (suffixed -2, -3… if it exists) from the default branch of the repository you choose, after a confirmation that states the repository, branch, files and commit message. A file that already exists on the default branch is updated. This is a parity gap, on purpose, with the tool these combinations come from: **no direct commit, no push to an existing branch**.

**Link the tests to the manual cases.** Optional, after a delivery, unticked by default: AutomatedTestName, AutomatedTestStorage and AutomatedTestType are written with your permissions, after a revision check. **AutomationStatus is never set to “Automated” for a skeleton**; AutomatedTestId is never written — the native association of Azure Test Plans targets tests published by a pipeline.
