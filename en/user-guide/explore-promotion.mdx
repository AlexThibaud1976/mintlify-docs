At the end of an exploratory session you can record whether the delivery you just tested may move to the **next environment stage** — and that decision is written where a change board actually looks.

- **A ladder per project** — every project starts with a suggested ladder, **TEST → QUAL → PROD**. It is set in *Project settings › Extensions › TestPulse Studio › Verdict and campaigns*, reserved for project administrators: they rename, reorder, add or remove stages there, together with reporting the decision on the host work item, and the same ladder is seen by every tester of the project. Members no longer change it from their own preferences. A stage name may not be empty, may not repeat an existing one (case ignored), and may not contain `;`, `,`, `>` or `:` — the message names the rule you hit. **Restore TEST › QUAL › PROD** brings the default back.
- **Turning it off** — remove every stage and save. The feature is then **disabled for the whole project**: no selector when starting a session, no block when closing one, no band in the report. An empty ladder and a project that was never configured are stored as two different things; a configuration that cannot be read falls back to the suggested ladder rather than silently disabling anything.
- **Choosing the stage** — the **Environment** selector on the start form is optional and nothing is preselected. Without a stage, no decision is offered when you close, and the session behaves exactly as it did before. If the stage is later renamed or removed from the ladder, the session simply gets no decision block — nothing is guessed.
- **Deciding** — a **Promotion decision** block appears under the verdict, showing the transition it applies to (**QUAL → PROD**, or **Validated in PROD** on the last stage) and three values: **OK**, **Reserved**, **Blocked**. A comment is required for the last two. Clicking the active value again clears it. The decision is optional, and **final** once the session is closed: a mistake is corrected by running another session, never by editing.
- **What is written, and where** — a preview box in the closing dialog names the target and the exact tag before you act. The decision lands as a queryable **tag** on the session task, as a **coloured band** on the session PDF cover page (transition, value, comment, and an audit line naming the author, the date and the outcome of the work item write), and as a **tag plus one discussion comment on the work item the session was run from**.
- **The write on the work item** — this is the only place where TestPulse Studio writes to a work item it did not create, and it is bounded: **one target** (that work item, never another), **two fields** (its tags and one discussion comment — never a state, an assignment or a link), **one trigger** (your click on *Close* with a decision selected), **one switch** (an administrator can turn it off project-wide). Only a previous decision on the **same transition** is replaced, so decisions taken on earlier stages stay on the work item.
- **Rights, and what happens without them** — the write uses the permission the Exploration tab already requires, but you also need write access to that particular work item. If Azure DevOps refuses, the session still closes, the task is still created and the decision is still recorded and exported; the message quotes Azure DevOps's own wording, and the re-approval banner is **not** raised — the permission is granted, the right on that work item is what is missing. If the form you are looking at carries unsaved changes, the write is skipped rather than risking a revision conflict that would make your own save fail, and you are told what to do. Resuming an interrupted closing never posts a second comment.
- **Never an indicator** — the promotion decision does not count toward a pass rate, a quality score, a GO / NO-GO verdict, or any campaign export. Like the session verdict, it lives in the exploratory domain only.
