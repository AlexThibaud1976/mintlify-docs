**Where and who.** The test grid is set in **Project settings › Extensions › TestPulse Studio › Test grid**, and is **reserved for project administrators**. It lives in the project configuration: adopt a baseline in *Configuration profiles* first — until then, the built-in grid applies and can only be read. Like every page of the administration, a change stays a draft until **Save**, in the banner at the top.

**Three axes, named as in the ISTQB Foundation syllabus.** The page opens with a banner, **How Studio sorts a test**, then shows one list per axis and, beside it, the **detail of the chosen entry**. **Test levels** — *Component testing*, *Component integration testing*, *System testing*, *System integration testing*, *Acceptance testing* — are closed: they can be renamed and their rules changed, never added or deleted. **Test types** — *Functional testing* and the ISO/IEC 25010 quality characteristics (*Performance efficiency*, *Compatibility*, *Usability* with *Accessibility* under it, *Reliability*, *Security*, *Maintainability*, *Portability*) — and **cross-cutting objectives** — *Confirmation testing*, *Regression testing*, *Maintenance testing* — can be extended with your own entries. A test may carry one level, several types and several objectives.

**Why regression is not a type.** Regression testing is a *purpose* — re-running tests after a change — that applies to functional as well as non-functional tests, at any level. It is therefore an objective of the grid, not a type. Likewise, *UAT* is the acceptance **level**, and *Integration* the system integration **level**.

**Techniques are not in the grid.** The five test design techniques of the syllabus — *Equivalence partitioning*, *Boundary value analysis*, *Decision table testing*, *State transition testing*, *Error guessing* — are chosen when designing tests, not detected in a plan. The former nominal and negative cases were the valid and invalid partitions of equivalence partitioning: they are now counted as equivalence partitioning.

**Expected by default.** Only *Functional testing* is expected by default in the built-in grid. Built-in entries can be renamed, marked not expected, given design guidance and have their rules changed; they cannot be deleted.

**How Studio sorts a test.** Studio reads four things about a test: its **tags**, its **suite** name, its **area path** and its **title**. For each entry, it tries the entry's conditions in this order — tags, then suite, area path, title — and **the first one that matches puts the test in the entry**. Every entry with a matching condition is kept: a test can carry **several entries of the same axis**. Every entry is recognised first by its canonical tag, always on — `niveau:<name>` for a level, `type:<name>` for a type, `objectif:<name>` for an objective (for instance `niveau:acceptance`, `type:performance`, `objectif:regression`) — then by usual French and English labels. Tags already written on test cases are never rewritten: the former `type:uat`, `type:integration` and `type:regression` are still recognised. Comparisons ignore case and accents; *contains* looks for a **whole word or phrase**. Detection only reads what is already loaded, with no extra call.

**The detail of an entry.** Its **Label**; **Recognised when…** — line 0 is the canonical tag, always on, then each condition with its readable sentence (for instance « → the test title contains the word “injection” »); ↑ and ↓ move a condition among those of the same source, and an empty pattern blocks saving; **In every plan** — expected or not, with a minimum of one test, N tests or N % of the plan: this is the **project default**, which a profile can change in *Configuration profiles › Expected grid*; **Design instruction**, sent to the model when it designs a test of this type. **+ Add a type** and **+ Add an objective** extend the grid; an added entry can be deleted with **Delete…**.

**Untyped tests.** A test that no condition recognises stays **untyped**: nothing is guessed; it is flagged, with no effect on the verdict. When area-path rules exist but an area path could not be read, TestPulse Studio says so instead of reporting the entry as missing.

**Test the detection** — describe a test (title, suite, area path, tags), or pick one of the three examples, and see, axis by axis, where Studio sorts it and which condition decided. It is computed on the draft, with the real detection, and with no call to Azure DevOps.

**Orphaned classifications.** When AI classifications still point to a type removed from the grid, a note at the top of the page counts them — reports ignore them — and **Purge…** removes them after confirmation.

**Moving from the former catalogue.** The first time a project administrator opens the administration, the former catalogue is moved to the grid **once**, with the same save as any change (a concurrent change is detected, nothing is overwritten), and the change is logged in *AI assistant › Log and failures*, under *Grid*. Nothing is lost: labels you typed, rules you added, design guidance and what the project expected are kept. *Functional* stays a type; *Regression* becomes an objective; *Integration* becomes *System integration testing* and *UAT* becomes *Acceptance testing* (levels); *Accessibility*, *Performance* and *Security* stay types; your own entries become types. *Boundaries & negative paths* is **removed** — it is a technique, *Boundary value analysis* — and a note says so; tests already classified under it stay readable as a « former type », never rewritten. Until an administrator has opened the administration, every member already **reads** the grid through the same correspondence, with nothing written. Accepted AI classifications are moved at their first reading, by any member. Nothing is written in Azure DevOps.

**What is expected, per profile.** *Configuration profiles › Expected grid*: for each entry, by axis, *inherit*, *expected* or *not expected*, and an optional minimum (N tests, or N % of the plan). It resolves like every other profile setting — the plan's profile, then the project default, then what *In every plan* says in the grid.

**The Design section.** It is set for the whole project, on the *Requirements and design* page of the administration (no longer per plan profile); it sets what a test generation proposes by default: the **default level** (product default: *System testing*), the **default type** (product default: *Functional testing*), the **allowed techniques** (by default, all five) and the **judge check** (on by default, but only when a judge model is set in *AI assistant › Connection*). It is overridden as a whole, with its provenance, and shown read-only in *My preferences › Project rules*.

**Never a factor of the verdict.** An expected level, type or objective that is missing, or below its minimum, becomes a **point of attention**; the verdict and the quality score do not depend on it. See [The test grid in the report](/en/user-guide/test-types-report).
