**Where.** Under the list of files of **Read the code** (step 0 **Requirement** of **Design**, and the **Exigence** tab). **Compare with the code** is active once code has been read and ticked, the **Source code** data category is on and the **Comparison with the code** function is on (**AI assistant › Functions and data**); otherwise the button says why.

**The gaps.** The AI assistant compares the requirement, the test model and the existing cases with the files read. Each gap has its kind — rule missing from the code read, check missing from the requirement, different value, cannot conclude from the code —, the rule concerned, the lines of code cited (highlighted, with a link to the file at the version read) and a confidence. A rule without trace is said to be absent **from the files read**: the code read is partial.

**Checked by Studio.** A gap that cites a file that was not sent, lines outside the excerpt sent, an unknown rule or a value that is not in the cited lines is discarded and counted at the bottom, never shown as a result.

**Exact citations.** Every file read is sent with its line numbers, so the assistant cites the numbers it sees. A gap whose cited lines are all blank, or whose quoted code (between backticks) is not in the file read, is discarded too. When the quoted code is a few lines away (at most 10) in the same file, Studio moves the citation onto it and says **citation relocated**. A proposed value must be in the cited lines — or be accepted by a regular expression written there —, and a rule taken from the code must carry its numbers and quoted texts from those lines. A gap “rule missing from the code read” whose rule has at least two of its elements (numbers, quoted texts, message codes, capitalised words) in one file read becomes **cannot conclude from the code**, and Studio says where those elements appear.

**Unread dependencies.** Under the list of files, Studio lists, without AI, the modules imported by a ticked file that were not read (relative imports of JavaScript and TypeScript files), checked at the same version: not ticked — **Add to the selection** —, in the repository but not read — **Add to the selection** reads it at the same version, within the reading caps, or says why it cannot —, missing from the repository, or not checked. A gap that the assistant attaches to a question of the requirement (Q-nn) says **question Q-nn**, never “rule missing”; a citation is never moved onto a declaration line (`import`, `type`, `interface`). Code quoted between backticks is checked with tolerance: a quotation of the requirement, or a fragment without any code character, is not checked; `==` and `===`, straight and curly quotes are the same, `…` stands for anything; the fragment is looked for in the whole cited file, then in the other files read. When a gap is discarded for code not found, the missing fragment is shown. A proposal that a comment of its cited lines — or the text of one of its other citations, such as a README line (“no lock against two simultaneous saves”) — contradicts (`// No lock: …`) is discarded. A “rule taken from the code” that the cited code contradicts is never shown as taken from the code: it is discarded when it refuses what a cited line accepts (“the `L-` prefix is not accepted” against `// also accepts the “L-” prefix`) or when its numbers are not the bounds of the cited code (“8 to 20” against `phone.length < 10`). When a screen read limits a field more strictly than the validator read (`maxLength 20` against `> 30`), Studio adds the gap itself: beyond the screen limit, the rule can only be tested through the API. **Question for the PO** adds a question of priority important. The assistant is told which dependencies were not read and must not assume what they do.

**A failure keeps the result.** If a comparison fails or is cancelled, the previous result stays on screen (with its time) under the message, and the questions already added stay added.

**What you do with a gap.** **Question for the PO** adds it to the requirement assessment (source “code”, priority set by Studio); **Copy** puts it on the clipboard; **Ignore** puts it aside. Nothing is written to the story or to Azure DevOps.

**Proposals on the test model.** In Design, **Propose to the model** sends a proposal (a partition, a value, a rule numbered C-n, a corrected reference) to the model step, where you accept or refuse each one. The design is then recomputed by Studio: new coverage elements, new cases to write with the usual flow, existing cases to review (never changed). Cases that come from the code are tagged “source:code”.
